# Write — reports for playtest inspection

These classes render a session's evidence as human-readable output. Every one draws only what the record captured, making no inference beyond what the read and check layers provide.

```
Write/
├─ DrawTickPicture.cs      `--picture` and `--pictures`: one recorded tick drawn to a PNG — terrain, bodies, region, steering target, hostiles, drops, legend
├─ EncodePng.cs            an 8-bit RGB PNG with a hand-rolled CRC-32 and the framework's zlib, so no package and no graphics device
├─ ExplainOneTick.cs       `--explain`: everything the record holds about one tick, or the ticks in a window where something changed
├─ MultiRunReport.cs       compares runs by schema, source revision and configuration; prints shared and differing facts
├─ PaintOnARaster.cs       an in-memory RGB image: rectangles, discs, rings, lines and a 3×5 bitmap font
├─ WriteBehaviourParity.cs one row per behaviour the README specifies: the fixtures that grade it, and what this capture said
├─ WriteCourseTimeline.cs  one row per decision: what the census admitted, what the course ordered and bound, what it cost
└─ WritePlaytestHtml.cs    self-contained HTML with scrollable event timeline, tick navigation and per-kind filtering
```

**`WriteBehaviourParity` is a coverage table before it is a comparison, and its empty rows are what it is for.** Every check in this tool fires on a condition somebody imagined, so a behaviour nobody wrote a fixture or a check for produces no finding *and no skip* — invisible, in exactly the way the census this tool prints above its findings exists to stop for categories of event. The README's Behaviour By Behaviour table is the nearest thing the project has to a specification, so it is the list coverage is counted against, and it is read at run time so a behaviour added there appears as an unmapped row rather than being silently absent. On the 22 September 2026 capture it reads 32 behaviours: one named by no fixture at all, one the play agrees with, six it contradicts, five that play never exercised, seven silent with nothing to say whether they occurred, and thirteen nothing here measures.

**A check that ran and found nothing is three answers, and reading it as one was this page's own false negative.** Its first version turned silence into "play agrees", so on that capture it asserted agreement with *Self-preservation* over a session holding zero damage events and zero downings, with *Recovering when it cannot follow* over one where `recovery_active` was false on all 2,340 rows, and with *Breaking containers* over one whose census never admitted a pot — thirteen of them, and the same thirteen on a capture four days older, which is the tell that the number was a function of which checks ran rather than of the play. A false negative in a coverage table is worse than a false positive in a findings block, because the findings block is read adversarially and the coverage table is read as reassurance. So a row may declare a **witness** — one piece of the capture's own evidence that the behaviour occurred at all — and the verdict is three-valued the way the light and reach senses are: `play agrees` only where the witness saw it happen, `not exercised` where the witness proves it did not, `silent` where nobody can say. A row with no witness stays in the third rather than being promoted, which is what makes declaring one worth doing; eight are declared and the rest are honestly silent. **A witness whose producer moves domains has to follow it by schema, and *Breaking containers* is the one that did.** From 0.47.0 pots are a `collect-target` opportunity rather than their own `pot-target` domain, so reading `pot-target` on a new capture would answer "not exercised" for ever — a silent no in the shape of an observation. The witness reads `pot-target`'s usable count below 0.47.0 and, from it, the `container-usable:N` the recorder writes inside every `course-admitted:` entry, which counts a candidate by the Container need it carries rather than by the domain it sits in, so it survives the pot moving again.

The fixture column is headed `cases N` rather than `fixtures N` for a reason that only shows beside the verdict: "fixtures 2 · play agrees" is read as two fixtures passing and the play agreeing with them, and this page makes neither claim.

Three of its properties are load-bearing. **The mapping is declared rather than matched**, because a keyword match would pair a row about protecting the player with every check whose name holds the word "player", and a claim somebody made can be argued with. **It names check types rather than check names**, so renaming a check class is a compile error where a renamed string would be a row that silently stops matching; the fixture names cannot be types, so the self-test pins them against the instruments that register them — and that pin was useless until it stopped searching this tool's own tree, because the table's literals live here and a search across all of `Tools/` finds a file's own contents. **It does not read the fixture's verdict**, only that the fixture exists: a case's pass or fail lives in `Tools/Ledger/runs/`, which holds whichever runs happen to be committed at whichever commits, and a report about one capture that changed its answer with the state of that store would be reporting on the store. It closes by asking the same question backwards — which checks no behaviour row claims — because a check nobody could name a behaviour for is either an instrument check or a question the specification has no row for, and the second is a gap in the specification rather than in the reader.

**`WriteCourseTimeline` and `../Read/DescribeCourseDecisions` narrate the same session and answer different questions, and the split is worth stating because two pages describing one record is how documentation drifts.** The narration reads the `course-decision` occurrences and coalesces them on *what was decided* — reason, activity, bound purpose — which answers "what was it doing at tick 8127". The timeline is keyed on the decision *identity* the rows carry in `choice_id` since schema 0.43.0, and joins to each the four things the occurrence payload does not hold: the per-domain census admission from the `decision` occurrence, the published order and its runner-up from the row, and what the decision cost. Those are what every reading of the 22 September 2026 capture had to assemble by script.

**The release reason rides on an unsettled record, so no one record of a decision holds both its numbers and why it ended.** `DecideCourseEachTick` traces the release on the tick after publication and that record is unsettled, while the settled record is the one carrying the steps, the pricing and the refusals. On the 22 September 2026 capture the two are perfectly disjoint across all 2,340 payloads — settled with no release 1,364 times, unsettled with a release 976, no other combination — so any reader that picks one record per decision and reads both off it is choosing which of the two columns to blank. That is not a hypothetical: the timeline's first version preferred the settled payload and printed a dash in `released` on 1,068 of 1,068 decisions while the producer had written 976 reasons, and `a1b9857` had found the identical shape in the release contract three hours earlier the same afternoon. Both times the fixture was what hid it, because every payload it wrote was settled with an empty release. **A fixture for anything reading a course decision varies `settled` and `release-reason` together, or it is testing a record the producer does not write.**

Two consequences follow for the fold. **A span that traced no release is not a decision that was not released** — 463 of that capture's 1,092 traced none, and treating the dash as a value split the first four hundred ticks into alternating one-decision runs while nothing about the course had changed, so two reasons are compared only when both are there; populating the column naively took the table from 57 runs to 81 before that rule went in, and restoring it brings the count back to exactly 57 with the column full. And because of that, **the comparison is against the release the run has accumulated, not against its representative's**, since a representative that traced none would otherwise let a third member's different reason fold in silently under the second's.

Three further properties of that table were each a way to get it wrong. **A decision's payload is not on its own `choice_tick`** — the identity advances when a decision is reached and the payload is written when an outcome is traced, so 2,340 payloads landed on 1,364 ticks of that capture and a lookup keyed on the decision tick printed dashes on about half the rows; the payloads inside a decision's own tick span are its own. **A decision that traced no payload is not a difference**, so it folds into the run it sits in and the count of undescribed decisions is stated once in the header, because treating the absence as a value split the table into a hundred runs a third of which were one blank decision each. And **the abridged view keeps both ends**, because a session's diagnosis is usually at its end: the first thirty runs of that capture stop at tick 788 and hide the row the whole report is read for, which is 258 decisions from tick 1,821 binding nothing while the census admitted three combat targets and four drops.

**`ExplainOneTick` answers "what was going on at tick N" in the order a diagnosis asks it, and it reads nothing a page beside it does not already read.** The sections run: what the course decided (the decision's span by `choice_id`, its numbers and its release through `WriteCourseTimeline.PickFromSpan`, the refusal tally, the leaders per domain with their value terms, the order columns), what each census admitted, what the companion did (request, spot, navigator, controls, hands, the `movement-state` and `navigation-state` it was acting on, and any other occurrence on that tick), where the bodies were (from `../Read/ReconstructTheSceneAtATick.cs`), what the tick cost (phases, the frame columns, the tick's own section profile, allocation, and its verdict against `cost_fence_ms` with the `cost-spike` tree when there is one), and the findings whose span lies within sixty ticks of it from `Program.Evaluate`. Three rules keep it from lying. **A column the capture lacks prints as absent and is listed again at the end with the schema**, because a blank reads as an observation — on the 22 September 2026 capture that closing line names nine columns, the frame ledger, the section profile, the allocation pair and the fence among them. **The two periodic sources say how old they are**: the census, the leaders and the refusal tally ride on the `decision` occurrence, which lands on 469 of that capture's 2,340 ticks and on 46 of its world run's, and only a decision that priced orders names leaders, so the explanation reads the latest occurrence that carries each and prints its tick. **The decision's numbers and its release come off different records** for the reason the course timeline's paragraph above gives, through the same method, so the table and the explanation cannot come to disagree about one decision. The window form, `--explain <capture> <from>-<to>`, prints one line per tick where the action, the decision identity, the request, the region kind, the navigator status, the control source, the two hands, the threat count or the loot count changed, or the brain went over its fence; a watched column the capture lacks is named once rather than read as never changing.

**`DrawTickPicture` draws a recorded tick for a reader who may not open the game, and an empty patch in it means the record did not hold that thing.** It exists because the owner reads play by looking and every agent working here is barred from opening a window on his machine, so a picture has to be made with no graphics device at all: an in-memory raster (`PaintOnARaster`) written by `EncodePng`, whose CRC-32 is written here because the framework's own lives in a package this reader will not take, and whose compression is `ZLibStream`. The terrain is `../../NavReplay/ReconstructTerrainWindow.cs`, the same reconstruction a cut scenario uses, joined on the recorder's stopwatch; where no chunk snapshot reached the window it falls back to the terrain a `combat-snapshot` carried at or before the tick, and the header says which it used. Everything else is `../Read/ReconstructTheSceneAtATick.cs`. The window is cut around the orb, the player's body, the intent region, the destination and the steering target with eight tiles of margin, grown to at least 72 by 44 tiles and widened for hostiles and drops up to 180 by 110; anything beyond is counted as off the picture. Three rules make it readable rather than merely drawn. **Unknown terrain is grey with a diagonal hatch and is never the colour of rock**, because the extractor's rule — close an unknown tile — is right for a route search and wrong for a picture that would then show a wall nobody saw. **Only an NPC the combat census or a combat snapshot held is drawn as a hostile**; one placed by a spawn or a damage record alone is an "other npc" in violet, because on the 22 September capture that rule is what separates a squirrel and three fireflies from the zombies. **The legend is in painting order, background to foreground** — solid, pass-through, platform, water, lava, honey, shimmer, air, unknown, orb trail, player trail, intent region, orb to lookahead, destination, navigator goal, activity target, drop, other npc, hostile, hostile over sixty ticks old, player, orb — so the orb and the player are never hidden, and `--pictures` prints that order above its file list. The header names the tile rectangle, so any mark reads back to a world coordinate; y grows downward in the world and the image alike. No schema records a route's corners, so what is drawn is a straight line from the orb to its `lookahead` and a dashed straight line on to its `spot`; it is not the route, and it can cross a wall the route goes round.

`--pictures <dir>` rides on the ordinary report: every printed definitive and potential line, after folding, gets a PNG drawn at its first tick, named `NN-<severity>-tick-<T>.png`, and a `picture` line naming the file and what it drew. A finding that names no tick, or a tick the capture cannot centre a picture on, gets a `picture  none: <why>` line instead of taking the report down. A finding spanning the whole capture is drawn at its first tick, which on the 22 September capture is tick 1, before any terrain snapshot existed, and the picture says so.

The HTML scrubber plots one companion position per sample, `npc_px`, which is the orb's centre in whole pixels. It no longer reconstructs a centre from a left edge and a width, because the record carries neither and there is no second body to plot beside the first. A sample whose `npc_px` is absent or unparseable leaves the companion trail empty for that tick rather than drawing a body at the origin.

**`MultiRunReport` folds its findings through `Program.Fold`, the same way the ordinary report does, and it did not until 22 September 2026.** One session printed two ways by two pages of one tool is the drift this tree bans, and the difference was real rather than theoretical: at `57db4da` the 22 September capture produced 1,089 definitive findings from two classes, and this page printed a paragraph for each while `Program.Main` printed eight lines. Nothing on disk exercises it now — the checks that produced those 1,089 are fixed and the 18 September capture produces no definitive finding at all — so it is consistency ahead of the next noisy capture rather than a repair of an observed page, and the comment at the site says so.

The HTML viewer is a bounded inspection surface: it holds enough context to diagnose one session, preserves event ordering and tick identity, and discloses every loss (cut rows, malformed entries, missing sidecars, interrupted capture). The multi-run report establishes whether runs can be compared and what differed between them; both kinds exit 0 when no definitive finding exists and 1 when one does, so they are checks and not only reports.
