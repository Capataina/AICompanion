# SessionReport — the reader for a playtest

**A stationary test cannot see a hunt that walks, and one target's evidence cannot describe every target.** The evidence check complements the stationary-hunt check by finding sustained fresh samples on which every target the census admitted read as not observed to the binder that had to use it. Between schema 0.40.0 and 0.45.0 it could not run at all: it read `target_evidence` and `target_evidence_age` as the arsenal's own bounded shortlist of rejected weapon-target pairs, the weapon block's rename took those columns, and the check has been a named skip on every capture since. The two names are back with the *course's* meaning — `<domain>=<fact key>:<evidence>:<observed>/<total>` — which is the measurement six independent readings of the 22 September 2026 capture each named as the one that would settle its census-against-binder contradiction and none could take. Its result is potential: a target reading unresolved for a few ticks is a census sweeping or a model query outstanding, and only a sustained stretch of it beside a fight that never fires is worth opening. Because the two columns changed meaning without changing name, the check names a 0.45.0-only witness column it never reads, so a pre-0.40.0 capture carrying the arsenal's format under those names skips by name rather than being parsed confidently as something else.

Ordinary lack-of-progress inference accepts only recorded ordinary movement owners (`travel`, `seeking-destination` and the legacy `navigation`). Safety, recovery, clearance and unknown owners remain visible in the chronology but cannot be charged to a retained ordinary activity. New owner names need an explicit attribution decision before joining this check. `accompany`, the owner that moves the body about the player's region once it is inside, was decided on 15 September 2026: it is an ordinary owner for the control-grant check, and it is not a stall candidate here, because it holds no chosen place to be stalled on the way to — a body accompanying the player is already where it was asked to be.

A downing transition warrants investigation but does not prove avoidability. The reader preserves the observed transition and bounded preceding sample context as a potential issue, without assuming pre-boss enemies or available escape routes. Sample counts are not elapsed seconds in sparse recordings.

Follow decisions require `brain_fresh`: when a downed companion stops executing its brain, the previous action and route fields remain sticky. Those rows end a follow-stall interval and cannot count as a newly selected follow response. Missing freshness is reduced coverage, not evidence of an active decision.

Follow checks recognise historical walk-with rows and current keep-company rows. Keeping company includes resting and local movement, so only its WithPlayer request establishes reunion for follow diagnosis and departure-response timing. A label alone cannot turn resting into a failed route. Legacy names remain a reader compatibility contract for existing telemetry, not alternative production behaviours.

The record was never the problem; the reading was. A session is tens of thousands of rows across eighty-odd columns, every diagnosis this project has made from one was a hand-rolled column sum, and the columns move whenever the brain grows a new fact — which on 2026-09-09 produced a reported mean distance of three and a half thousand tiles from an index that had shifted by two while nobody noticed. This tool turns a session into a verdict: what is definitely wrong, what is probably wrong, and what merely looks odd.

```
SessionReport/
├─ CLAUDE.md
├─ SessionReport.csproj   a console reader linking the pure course-snapshot contract and NavReplay's terrain reconstruction, without Terraria
├─ Program.cs             resolve the file, run every check, exit non-zero on a definitive finding
├─ Session.cs             the parsed file — columns addressed by name
├─ Finding.cs             severities, the check contract, and the coverage contract
├─ Read/                  parser, stretches, God's Eye, attempt joins, chronicle, session description, where the time goes
├─ Checks/                one file per question the record can answer
├─ Measures/              the numbers a play holds, emitted as ledger rows and never graded here
├─ Write/                 the decision table, the HTML timeline and multi-run provenance
└─ Tests/                 ChronicleTests on synthetic records, PlayMeasureTests on a real capture
```

**A check decides and a measure does not, and the split is load-bearing.** A check knows a rule the producer guarantees and reports a record that breaks it, which is why it can be Definitive with no threshold in it. A measure says the companion trailed the travelling player by more than three tiles on 71.5% of rows and stops there; whether that is bad is a question about the design, so the pass line lives in the verification plan and travels as a tag on the row. Folding the two together is how a number nobody declared becomes a pass line by accident. `Measures/CLAUDE.md` owns the reading conventions, each of which was a way to get the arithmetic wrong.

## The reader caught up with the recorder on 21 September, and the order of the three course files is the point

The recording side of the retained-course brain ran ahead of the reading side for the whole migration: typed course records, the bounded ordered transport and schema 0.41.0 all landed while exactly one of the four planned reader files existed. The whole argument for that brain was that after a play a poor decision, a stale model, an invalid binding and an effect that never arrived would be distinguishable — and that distinction lives here, in a reader that until `c16fe4d` could not read a decision at all.

Three files close it and they answer different questions in a fixed order, which is why there are three rather than one:

```
ReadCourseChronicle    can the evidence be trusted?   schema, envelope, snapshot manifests, terminal
                                                      closure → coverage, and never a story
ReadCourseDecisions    what does the record say?      the course-decision payload as a record —
                                                      reason, activity, settled, bound purpose, steps,
                                                      orders priced and refused, search exhaustion,
                                                      release reason — counting what it could not read
DescribeCourseDecisions  what happened?               those records narrated, coalesced on reason,
                                                      activity and bound purpose
```

A fourth page sits under those three and is the one to read first: `Write/WriteCourseTimeline.cs` prints one row per *decision* — keyed on `choice_id`, folded where consecutive decisions say the same thing — carrying what each domain's census admitted, what the course ordered, what it bound, what released it and what it cost. It is a different question from the narration above, which coalesces occurrences on what was decided; `Write/CLAUDE.md` owns the split and the three joins that were each a way to get it wrong. On the 22 September 2026 capture its last row is the whole diagnosis: 258 decisions from tick 1,821 to the end, keeping company, zero steps, one order priced and twenty-eight refused, beside a census admitting three combat targets and four drops.

A fifth file asks the question none of those can: `Checks/CheckTheCensusAgainstItsBinder.cs` joins the census admissions on the periodic `decision` occurrence to the refusal tallies on the per-tick `course-decision` payload, and reports a domain admitted usable whose every order the same decision refused for want of an observed target. That is the whole of the 22 September 2026 capture's "not attacking and not collecting" symptom, it was visible in one field of one occurrence, and six independent readings each found it by hand because nothing here asked. `Checks/CLAUDE.md` carries the join, the grade and what the carried admission costs.

The gate prints above the story in `Program`, deliberately, so a story is never read without the statement of how much of it is there. `Checks/CheckCourseDecisions.cs` restates producer guarantees with no threshold in any of them — a decision's published refusal tallies cannot account for more orders than the same record says it refused, a purpose read off the bound step means a course with at least that step, and every path through the owner names a reason — so a violation is Definitive; a capture new enough to hold decisions and holding none reports Potential rather than passing, because measuring nothing and finding nothing read identically. `Measures/MeasureCourseWork.cs` grades none of it.

**A combat decision is audited by a different tool and read back here.** `Read/DescribeCombatAudit.cs` renders the report's Combat decisions section from the `-combat-audit.json` sidecar that `../CombatAudit` writes beside a capture, and it adds no judgement of its own — it names the replay divergences with their generator attributions, grades the hold and the weight sweep, and says plainly when the sidecar is missing, corrupt or written for another capture. A missing sidecar reads as "unmeasured, not clean", because a combat section that vanished when the audit never ran would read as a clean fight.

`--measures <capture>` runs the measures alone; the ordinary report runs them above the findings. With `AIC_LEDGER_RUN` naming a run file the rows are recorded as well as printed, which is what `../backfill-capture.sh` uses to store a recording under the revision that wrote it. Each child folder lists its files.

**`dotnet run --project Tools/SessionReport` does not work in this repository and never has**, which every command line in this file used to say to do. `Directory.Build.rsp` sets `UseAppHost=false` for the SDK fault `Tools/WorldRun/CLAUDE.md` describes, so there is no native launcher for `dotnet run` to start and it exits 1 with "An error occurred trying to start process … No such file or directory" (reproduced 2026-09-22 in a worktree at `57db4da`). Build first and run the assembly:

```
sh Tools/build.sh session-report
dotnet Tools/SessionReport/bin/Debug/net8.0/SessionReport.dll <arguments>
```

## The operating manual

The default occurrence summary exposes the latest `tool-effect` in each displayed interval, including attempt identity and observed outcome. Full timeline output retains every captured effect. A successful call with no change remains visible without being labelled productive; tile removal does not imply collected yield. Older recordings with no such events cannot establish these tool outcomes.

Activity-state occurrences retain current purpose identity, phase, interruption reason and last termination. The default summary shows their latest state per interval, while the full timeline keeps each recorded transition. Suspension is distinct from unsuccessful tool execution and never automatically becomes a physical failure.

Attempt-outcome occurrences are grouped by activity and channel within each interval, with a count and the latest payload per group, so an interruption earlier in a window stays visible beside a completion later in it. The channel carries attribution beside a completion, so `Complete:Companion`, `Complete:Shared` and `Complete:Unattributed` are separate groups and a jointly finished vein never reads as the companion's own work. The status and cause are the activity's own conclusion from its evidence; the reader repeats them and does not reclassify an Interrupted attempt as failed work. Older recordings have no attempt occurrences, which is missing coverage rather than evidence that no attempt ended.

Method-assessment occurrences are grouped by actor, activity and recorded admission result within each summary interval. Counts and the latest payload for each result preserve a rejection even when admission follows in the same window. This is a summary of observed pre-activation queries, not an inference that travel or damage succeeded; the full timeline retains every assessment and its target identity. Missing assessments in older recordings do not establish that methods were checked successfully.

The writer declares text columns explicitly. Numeric validation consumes that declaration, with a named legacy set for older recordings; adding a reason string must not fabricate a malformed numeric-record finding. Outcome-aware attack recordings are not judged by the old maximum-damage-only weapon check, because sacrificing damage to remove an urgent threat is intentional. Their sequence estimates and alternatives remain inspectable evidence, not proof that the forecast was correct.

The multi-run reader opens with provenance: schema, source_revision, tree, terraria, tml_assembly, runtime, os and mods from each run's metadata preamble, then the configuration keys a run started under, each marked shared, differing (with the runs holding each value) or unrecorded for the runs that lack it. It then says whether the runs may be joined. A join reads one run's evidence as if another's code had produced it, so it is refused when any build key differs, and refused as well when any run lacks a clean known source revision, because runs agreeing only that their source is unknown or dirty cannot be shown to be one build; only runs recording one clean revision are called joinable. A configuration difference is stated beside the runs and never refuses, because it changes what the companion chose to do rather than which code chose it. Captures older than schema 0.28.0 record no source revision, so every comparison of them is refused. The writer packs terraria, tml_assembly, runtime and os into one metadata line, so the reader splits a value whose later segments are all `key=value`; the mods list has no equals signs and stays whole. A field a run did not record is never filled from the current checkout, because the checkout is not the build that recorded it. It then prints the same full-source findings and coverage gaps as the single-run reader, separately for each session. An arrived navigator with an unsatisfied follow objective and no controls is a contract contradiction. A stationary submerged body or an ineffective hunt is a potential issue whose report carries control source and rejection/escape evidence when available; neither observation alone proves physical reachability.

The HTML viewer keeps source-run identity, a sample scrubber, exact tick entry, event-kind filtering, previous/next event navigation, every sampled TSV field, and full retained event payloads. It streams sparse events across the entire run into bounded per-kind reservoirs so cosmetic terrain contacts cannot erase a late injury or death. Every omitted sample/event, malformed row, missing sidecar and missing normal closure is disclosed. HTML is a bounded inspection view; the ordinary and multi-run reports still analyse the full source records and share definitive-finding exit semantics. The writer's caps own output size; the UI never implies that its sampled trail is a complete recording or draws invented terrain.

```
R=Tools/SessionReport/bin/Debug/net8.0/SessionReport.dll     # after sh Tools/build.sh session-report
dotnet $R Telemetry/<stamp>.tsv
dotnet $R Telemetry                                           # the newest session in the folder
dotnet $R --timeline Telemetry/<stamp>.tsv                    # complete chronological account
dotnet $R --multirun Telemetry/<a>.tsv Telemetry/<b>.tsv      # each run keeps its own coverage; exits 1 if any ordinary-report definitive finding exists
dotnet $R --html <out>.html Telemetry/<a>.tsv Telemetry/<b>.tsv  # headless, self-contained actor scrubber
dotnet $R --explain Telemetry/<stamp>.tsv 1820                # everything the record holds about one tick
dotnet $R --explain Telemetry/<stamp>.tsv 1800-1830           # the ticks in a window where something a diagnosis turns on changed
dotnet $R --self-test                                         # deterministic chronology parser and narration tests
```

Exit 0 when nothing definitive was found and 1 when something was, so the run is a check and not only a report. `--explain` is a question rather than a check and exits 0 whenever it could answer, 2 when the capture or the tick argument could not be read; `Write/CLAUDE.md` carries what it prints and why each periodic source says how old it is. The one-run folder form remains a newest-run convenience. `--multirun` and `--html` expand every `.tsv` in each supplied folder, preserving first and last captures rather than silently reducing a folder to one session; an unreadable selected TSV remains in the multi-run output as unavailable coverage and makes its verdict non-clean. The sibling `<stamp>-plans.txt` is read automatically when it sits beside the `.tsv`, and its window count and reasons are tallied in the header block with the replay command that opens them.

## The chronology says what the record saw, then labels the inference it earns

New records begin with a schema and UTC start metadata, then carry `wall_elapsed_ms` from the recorder's `Stopwatch` on every phase-labelled sample, whose phase reads `in_ai_after_contact_before_engine_move`. The companion's position is `npc_px`, the orb's centre in whole pixels, and `npc_vel` is its velocity: there is one body, so there is no observed-against-predicted pair to reconcile and no divergence reading to qualify. It coalesces equal state into intervals and prints changed liquid, activity, control source and hit events in tick order beside actual elapsed wall time. It calls a slope ascent or descent only when a floor-slope support and matching vertical displacement occur together, and it names that as an inference; it never guesses pond, hill or stairs from coordinates. That inference is the player's alone — he still rests on a support the recorder names, while the companion flies and has none. Player and companion hit events record final damage, direction and knockback; the player event names a source where Terraria exposes one, while the NPC hit callback has no attacker source and says so. A sustained active, non-reflex control request with one stable spot and no body movement is reported as an **inferred lack of progress**, including its wall-time and tick interval; an intentional hold is not a failure. "Active" is read from the `control` cell, which is `desired=x,y`: a zero desire is a brake rather than a neutral, so any non-zero component is a request to move, and a predicate looking for the walking body's `move=`, `jump=1` or `fall=1` would be false on every row of every capture from here on. Follow diagnosis is separate: it needs an unsatisfied valid follow objective and no completed route step in the current window. Increasing direct distance is insufficient, because a valid C-turn can initially widen the gap while it completes waypoints. Remaining route time is displayed but never certifies progress, since it can fall while a frozen body spends an active step. Recovery-flight rows are excluded so stale `WithPlayer` state cannot become an ordinary follow failure. A distant moving player without later `walk-with` selection is an observed response-coverage oddity measured by `wall_elapsed_ms`, never frame time or automatic proof that work, guard, or recovery was wrong. Old files print one explicit unavailable line with every missing column, because partial chronology would otherwise read like an account of events the recorder never observed. The normal report is capped; `--timeline` prints every chronological event.

## Selections, attempts and grants are read by identity, and their contradictions need no threshold

The window summary groups occurrences by when they happened, which puts a completion beside a grant that belonged to a different attempt whenever both land in one window. `JoinAttemptEvidence` reads the same records by who they name instead. Outcomes and control grants join on `attempt-id`, which the activity owner draws from one process-wide counter, so it never repeats within a session even when a respawned companion builds a new brain (activity, comparison and grant identities do restart with a brain). A grant issued with no attempt open carries zero, which is every recovery and downed grant, and every safety grant in a capture from before 15 September 2026, because each of those branches suspends the activity before finalising; those are counted, not attached. From schema 0.25.0 a tool effect carries `activity-attempt-id`, the attempt open when Execute struck, and joins by that alone; zero means it struck with no attempt open, which is counted unjoined and is a contradiction of its own. Its `attempt=` is the tool instance's own counter and names nothing the owner knows. An older strike carries only `activity-id` and `choice-id`, so it joins through the TSV row at its tick, which names the attempt open when the row was written, or the attempt of the same activity that closed on that tick — an attempt can open, strike and be suspended by recovery inside one tick, leaving no row or grant that names it. Only with no such row does an older strike fall back to the one recorded outcome of its activity whose interval contains the tick. Each attempt line says which route joined its strikes, because a join by the producer's identity, by a row and by an interval are three different strengths of evidence. Whatever no identity resolves is printed as unjoined, and an attempt with grants or strikes but no outcome is printed as "outcome unrecorded", which means still open when capture ended or an occurrence that was lost. The default report shows the latest attempts, `--timeline` every attempt and every unjoined record, and the HTML scrubber the attempts that began by the selected tick.

The five checks beside it each restate a producer guarantee and name the line that makes a violation impossible, so a finding is Definitive without a tuned number:

- **A selected activity carried a usable or unresolved offer.** The evaluator refuses positive value beside any other eligibility and only positive nominations are selectable, so a selection whose own `<activity>_offer` reads known-unusable, forbidden, no-opportunity, deferred or not-compared contradicts the chooser. The action label and the offer columns are retained together from one comparison, so the check folds rows by `choice_id` and judges each comparison once, on its `choice_fresh` row; `brain_fresh` would be wrong here because recovery ticks, and safety ticks in older captures, run the brain without comparing. It proves the record and the chooser disagree; it says nothing about whether a usable offer was a good choice.
- **A selection changes only with a new comparison.** The current activity is replaced only inside a completed comparison, which also advances `choice_id`, so two consecutive rows with one id and two actions are a label that moved without a decision. EngineReplay fixtures that call the activity owner directly are not playtest recordings and can violate this.
- **Every record names an attempt under one activity and inside its interval.** Outcome ids are strictly increasing, one attempt id never names two activities across outcomes, grants, strikes on open-attempt rows and the rows' `attempt_end_*` columns, grants under an attempt fall inside its recorded ticks, rows strictly inside that interval name it open, and a strike's `choice-id` equals its tick's row. A strike carrying its own attempt must name a non-zero one, which its tick's row holds open or closed on that tick, and its tick must lie inside that attempt's recorded interval, because only an executing activity strikes and Execute runs after the attempt opens. It deliberately does not flag an outcome no row or grant ever named, for the one-tick attempt above.
- **Every claimed transfer arrived as pickups under its own attempt.** A Complete or Partial outcome claiming a yield must be matched by pickups naming that attempt, of that item, delivering at least the claimed quantity; the finding's title is "a completed transfer claim with no matching received quantity". It is Definitive over a whole occurrence stream and Potential when a sequence is missing, a line is malformed or the stream never closed, because then the pickup may have been lost from the record rather than never made. A capture older than schema 0.26.0 skips it by name.
- **Every control grant could have been issued as recorded.** A work-tool hand never comes with a suspending owner or with attempt zero, an unavailable hand appears exactly when the requested owner is downed, a suspending owner never carries an attempt, an open attempt means the Executing phase, and one engine tick holds one finalisation (a falling grant id is a new brain and is not judged). The rules read the requested owner, never the applied one, because a downed hold is legitimately applied as recovery clearance. `evade` is ordinary rather than suspending, because the evade layer bends the job's own controls without suspending its attempt, while `combat-spacing` and `combat-reflex` stay in the suspending set only so recordings made before the layer are still read correctly. An owner name outside the ordinary set (travel, seeking-destination, hold, evade) and the suspending set is printed as an oddity naming it, never judged, so a new producer owner needs a decision here before it is covered.

The two reach counts are `reach_any` and `reach_two_way` from schema 0.31.0, after the reach sense that owns both floods; before that they were `reach_n` and `returnable_n`. `ReturnableFitsInsideReach` and the body report name the new columns, so an older capture skips them rather than matching by position, which would be guessing that two differently-owned columns mean the same thing. The same release replaces `ambient` with `dark_near`, `dark_ahead` and `torch_reason`; no check read the old scalar, so nothing was lost by its going.

Schema 0.34.0 is the orb's row, and it is a larger break than any bump before it because it is a change of body rather than a change of instrumentation. Gone with the walking body: `ground`, `collide_x`, `collide_y`, `vel_cut`, `press`, `descend`, `breath`, `head_submerged`, `breath_ticks`, the divergence trio, the seven `edge_*` columns, `next_kind`, `npc_support`, `npc_width`, `npc_height` and both `observed_*` and `predicted_*` bodies. `path_steps` and `path_at` became `route_points` and `route_index`, and `edge_cache` became `clearance_builds`. Arriving: `route_remaining_px`, `lookahead`, `touched_wall`, `wall_normal`, `liquid`, `hurting`, `clearance`, `liquid_ticks` and `desired_vel`. The `control` cell reads `desired=x,y`, `sample_phase` reads `in_ai_after_contact_before_engine_move`, and `npc_px` is the orb's centre.

**The walker's columns are not an older version of the orb's, and the skip rule does not cover them.** A capture older than a *feature* is skipped by name, because the question still means something and the evidence is simply absent. A check about a fall-through press, a proven edge's tick count or the distance between two predicted bodies has no orb meaning at any age, so it is deleted rather than skipped — `Checks/CLAUDE.md` names the four that went and what each read. The dangerous case sits between the two: `npc_px` kept its name and changed its meaning from an after-helpers position anchored on the feet to the body's centre, so a check whose arithmetic depends on which one it is names a column only this schema carries and skips instead of quietly measuring the wrong point.

A capture older than the evidence is skipped by name, never passed. The offer check needs `<activity>_offer` columns, which schema 0.20.0 introduced; the attempt and grant checks need `activity_attempt_id` and `control_grant_id` in the header as the schema witness — an old sidecar with no grants and a new one with no grants look identical — and the sidecar itself. Because those requirements are not fixed column names, such checks implement `ICheckCoverage`, which `Program.Evaluate` asks after `Needs`, so the skip reaches the coverage block and the multi-run report alike.

**Schema 0.34.0 was the orb's row and the producer has moved on well past it, so the gap between what the recorder writes and what any capture on disk carries is the thing to know before reading a coverage block.** That gap closed on 22 September 2026 and it closed in both directions at once, which is why this paragraph is worth reading before a skip line is believed. The wired course brain was played that morning and wrote `2026-09-22_10-05-56-125` at schema **0.44.0**, so the course chronicle, the course decisions reader, the course check and `MeasureCourseWork` have now met real data and run rather than skip. **The coverage figure itself is not quoted here and should not be**: both halves of it move — the denominator with every check this tool gains, the numerator with every schema a capture predates — so a number written into this file is stale by the next lane and reads as authority while it lies. It came out as `41 of 46` on 22 September 2026 and it is printed at the top of every run; read it from the run. The recorder then reached **0.45.0** the same day, so the newest checks — the frame ledger, the decision audit, the revived combat-evidence check — skip by name on that capture and on every other, and the next play is the first input they will see. Both halves of that are normal and neither reads as a fault. What is *not* normal, and is the reason a check can be wrong on a capture it happily runs on: a column whose meaning moved under its own name. `choice_id` at 0.43.0 and `<activity>_offer` at 0.44.0 are both of those, and the two checks resting on them are the paragraph below.

**Two checks restated the family chooser's guarantees and were still grading them on a course capture, and together they produced 1,089 of that capture's 1,089 definitive findings.** Neither column moved name or position, so nothing could skip: `SelectedActivitiesHadAnEligibleOffer` read `not-compared` beside a selected keeping-company on 875 comparisons, and `not-compared` is the literal `ReadCourseWorthPerActivity` is documented to write for an activity the course mints no domain for — which keeping company always is, because an empty course *is* companionship. `ARetainedChoiceKeepsItsSelection` read 214 activity changes under one `choice_id`, which since 0.43.0 is the course's decision identity rather than a comparison the chooser advanced, so a decision spanning ticks with a changing bound activity contradicts nothing. The schema line is the only witness either has, and both now turn on it: the offer check exempts `not-compared` from 0.44.0 and keeps `KnownUnusable`/`NoOpportunity` as the contradiction that survives, and the retained-choice check skips by name from 0.43.0 while `TheBoundActivityHoldsWhileOneDecisionRuns` asks the course's version of its question at Potential. **The generalisable half is that the coverage block cannot see this class at all**: a check whose *producer* was replaced runs, finds plenty, and is confidently wrong, where a check whose *column* was removed skips and says so. Anything here resting on a guarantee `0bb2c8a` retired needs the same gate.

**Schema 0.46.0 is the third case, and it is the one every gate in this tool was blind to: a removal.** `AIC-419` deleted the family chooser on 22 September 2026 and the recorder stopped writing every column and board entry it owned — `<family>_prepared`/`_deferred`/`_prepare_ms`, `<activity>_time`, `<activity>_funnel` with the `candidate-funnel` occurrence, and the decision board's score list with its `factors:`, `family:` and `queries:` entries. `RecordBrainTelemetry.cs`'s own comment is the authority for that list and carries why each was safe to take. The reader's problem is that **every schema gate here is a floor**: `SchemaAtLeast` asks "is this capture new enough to carry the evidence", and a 0.46.0 capture answers yes to every question ever asked of it, including the ones whose evidence 0.46.0 is exactly what removed. So a reader of a retired column needs a *ceiling* beside its floor — `SchemaBelow`, against `ChooserColumnsRetired`, both beside `SchemaAtLeast` — and the answer is a named decline rather than an empty one.

The failure a ceiling prevents is not a crash, which is why nothing would have reported it. A reader of a deleted field finds an empty string, computes from it, and publishes a clean number: `MeasureHuntKnownUnusableShare` reads the board's `factors:` breakdown for hunting's own offer, and on a 0.46.0 capture every decision parses as unreadable, so both its shares report **0 over several hundred** on rows whose direction is "down" — a fall to zero against the 0.44.0 baseline, in the committed ledger, that nobody earned. Three readers needed the gate and they took three different answers, which is the part worth copying rather than the gate itself:

```
the measure whose evidence is gone        declines by name; the question cannot be asked
  MeasureHuntKnownUnusableShare

the check whose evidence survives and      runs, and names the retirement inside its finding;
whose decorations do not                   skipping a live question for a lost decoration
  HuntsWorthTakingAreTaken                 would lose more than it saved
   (`_time`, `_funnel`)

the census block whose whole section       says "retired at schema 0.46.0" once; a section that
is gone                                    silently disappears is the census failing at its own
  DescribeSession's funnel lines           job, which is to say what a capture does not carry
```

Worth knowing before trusting the pre-0.46.0 side of any of this: the 22 September capture is 0.44.0 and carries **zero** `factors:` entries in its whole sidecar, because `0bb2c8a` left `Chooser.LastScores` unfilled when the course took the tick. That measure had been reporting nothing for a day before the column was deleted; the retirement makes it official rather than causing it.

0.34.0 is still the floor the orb's own measures and geometry checks gate on, and **exactly one capture carries it**: `2026-09-15_08-30-31-684`, the first orb play (mod 0.26.0 from `6a2e59e`). On it the report finds no definitive issue, with the census's journey table among its named skips, and it was the first capture on which a check naming an orb column ran on real data rather than only on synthetic fixtures. Its coverage figure is read from the run for the reason above — `35 of 46` on 22 September 2026, against the `32 of 32` this file claimed for it until then, which had been wrong since long before anybody noticed. One real session is thin evidence for any check's silence — that play was hated on sight and read clean — which is why its stillness is now measured rather than detected (`Measures/CLAUDE.md`). The recordings either side of it split two ways rather than one: everything older is a walking body at 0.33.0 or below, and everything newer is an orb at up to 0.40.0 carrying columns this paragraph predates. Both directions are why a column whose *meaning* moved without its name moving needs a witness column in `Needs` rather than trusting the capture to be new — an old capture must not be judged by geometry measured from the wrong point, and a new one must not be assumed to carry evidence the producer added after it was written. `IdentityRulesStillMatchTheProducer` pins the producer literals the rules rest on — the owner names, the grant, strike and outcome payload order, both strike sites reading the owner's open attempt, the offer column format and the process-wide attempt counter — so a producer rename fails the self-test instead of silently making a rule unable to fire.

Arrival outside a purpose's success region became checkable at schema 0.27.0, when the positioner began publishing the region each destination was admitted against. `ClaimedArrivalsStayInsideTheirSuccessRegion` judges only rows whose `region_arrival` is not `-`, which the recorder writes only when the navigator reports Arrived on a tick the ordinary branch requested travel, and recomputes the geometry from the region columns rather than trusting the recorder's verdict. Its severity follows what the producer guarantees, not how bad the stall looks:

- a follow arrival outside the intent region the destination was admitted against is Definitive, because acceptance reserves the navigator's settle radius — the arrival radius plus the hover's drift — inside that region; with comfort narrower than that radius, the reservation is impossible and it is Potential. There is one box: the request's anchor is evidence of what was aimed at rather than a second acceptance box, which it stopped being when the region gained its own growth, so a body parked beside a far-off anchor is outside the region it was admitted to — as it always was
- a tool stand declared outside its own reach box is Definitive while reach never changed in the capture, because every stand a tool proof returns reaches its tile and the box is arithmetic
- a held tool arrival outside the box is Potential, naming the navigator's arrival radius against the band a searched stand is verified over — and a stand kept because the body already reached from it is verified at one pixel, which is why no arrival near a stand can be Definitive
- a held tool arrival inside the box, on rows whose activity still asked for its stand, is Potential: the remaining half of reach is a line to an exposed face, which the box does not hold
- a held arrival at a firing position where no arc now solves is Potential, since the target moves

A held arrival is half a second of claims, because a navigator that has arrived hovers around its goal inside the settle radius, so a sample that is not held is momentum still being shed rather than a body hovering where it was sent. Meeting places, roams and exact requests without a work tile declare no region and are never judged. Every geometry here is measured on the orb's centre, which is the one point the navigator, the region and the reach box all take: the recorder hands `npc.Center` to `SuccessRegion.Contains`, and `FindToolAccess.InReachBox` takes a centre against the tile's own centre with an eye height of zero. The self-test pins the arrival radius, that zero eye height, the box extents, the three stand sites declaring their tile, the region names, the follow arm reading its region alone, the arrival-claim gate and the column order.

A capture's provenance and closure are read at schema 0.28.0. Lines beginning `#` after the header are the closing trailer and become metadata, never ragged rows, and `ReadMetadata` reads the preamble and then only the file's tail for that trailer, so a multi-run comparison still costs a few lines per run. `TheCaptureWasClosed`, registered beside the column audit, reports a capture without `# end=` as a Potential "interrupted capture", because only a normal closure writes that line and a failed write or a killed game never reaches it; its detail says that rows since the last flush and the closing census, map and event closure may be missing. An end marker naming a row count the file does not hold is Definitive, because the recorder counts exactly the rows it wrote. An older capture skips the check by name. The session summary and the HTML coverage line share one statement of source revision, tree state and closure.

Recording cost and loss are read at schema 0.29.0. The summary's `recording` line gives the distribution of `record_ms` over the rows that carry one, with the floor-of-rank percentile MeasureBrainCost prints, and the last row's written, dropped, coalesced and evicted totals; a `retention` line repeats the capture's retention statement; the HTML coverage line carries the same recording statement. `NoOccurrenceWasDropped`, registered beside the closure check, reports any dropped occurrence as Potential and names the tick the drops began, because the sidecar cannot record its own loss and every event-based check after that tick has measured nothing. An older capture skips it by naming the missing column and states its cost as unrecorded, never as zero.

## Where the time goes is a block of the report and a measure of the ledger, from schema 0.48.0

**The report prints, above the measures, which sections of the brain a capture's time and memory went to and which dominated the ticks that stood out.** `Read/DescribeWhereTheTimeGoes.cs` is the block and `Measures/MeasureWhereTheTimeGoes.cs` its numbers, both reading one `Profile` so the report and the ledger cannot disagree: each section's share of the brain's time with its p50, p95, p99 and max self time a tick; how much of the profiled time fell outside each row's eight listed sections; the recorder's own subtree set against `record_ms` rather than `brain_ms`, because it is the previous row's recorder; brain and update-thread allocation a tick at p50 and p99, and the sections that allocated most; collections a minute by generation; the spike ticks, read as each row's `brain_ms` above its own `cost_fence_ms`; the worst spikes by name from the sidecar's `cost-spike` trees; and the five sections that dominated the spike ticks, each with its share there against its share on ordinary ticks.

**Three rules of reading it, each a way to get the arithmetic wrong.** A section absent from a row's eight counts as zero on that row, which understates it by at most that row's eighth-largest self time; the allocator shares are a lower bound for the same reason. A spike is the recorder's verdict read back — a dash in `cost_fence_ms` is a window still filling and never a zero fence, which is the mutation the self-test's spike count is proved against (it read 12 spikes instead of 2). And every row carries the timed and sampled tags, because every number here is a clock reading or derived from one. A capture below 0.48.0 is declined by the schema that first writes the profile, named in the block (`where the time goes  unrecorded — the file has no section profile (written from schema 0.48.0; this capture declares 0.44.0)`) and in the skipped measure, rather than read as zeros; the self-test's `TheSectionProfileIsReadAndAnOlderCaptureDeclinesByName` drives both halves and pins the producer's column names and occurrence fields by literal.

**What it said about its first real input**, the world run's replay of the 22 September capture on 24 September 2026 under a heavily loaded machine: `decide.course.snapshot.assistance.light` held 28.1% of the brain's time and 52% of its allocation, `…snapshot.gathering.ores` 16.5% and `senses.reach-flood` 11.4%; the two spike ticks were 84 ms with 74.9 ms of it in `decide.prepare.combat.export` — the combat snapshot the recorder writes every 120 ticks while a plan is held, charged to the decide phase — and 48 ms with 37.1 ms in `decide.course.discovery.mine-target`. Those are the profile's findings for whoever optimises next; none is a verdict here.

## A capture nobody played is refused as play, and only a preamble line separates the two

`../WorldRun` drives the mod's own recorder, so a world run writes a capture in exactly the format a playtest writes: every column, every occurrence, a normal closure, the same schema. **Nothing in the rows tells them apart** — the player track is a recorded one replayed, the hostiles are staged from the source capture's own events, and the recorder cannot see the difference. The preamble's `# synthetic=world-run;source-capture=<stamp>;note=…` line is the only thing that can, and it is written before the header goes out.

Two things happen when it is there. The summary opens with a `synthetic` line naming the producer and the capture it replays, and says that no reading of the numbers below is evidence about a play; and the span stops being described as play — the same figure reads "0m 38s of replayed ticks at sixty a tick, not of play" rather than "0m 38s of play". Everything else still runs, deliberately: a world run is a legitimate thing to read a report about, and the report's job is to say *what* it is reading rather than to refuse.

What does stop is the play-measure pins. Those are before-numbers about one human session, and a world run reproduces a track rather than a play, so `Tests/PlayMeasureTests.cs` files a `skipped` row naming the producer and the source capture. That is the same rule the absent-capture and old-schema branches follow, applied to the case that looks healthiest: pointed at a world run of the very capture the pins were taken from, the measures would produce a full set of confident numbers about the harness.

**The marker's note runs to the end of the line and has semicolons inside it**, and a reader that splits the whole value on `;` and calls any segment without an `=` the producer reports half that sentence as the name of the harness — which this reader did the first time it met a real marker rather than a fixture. The producer is the first segment; the note is everything after `note=`, unsplit. The producer is also read as written rather than matched against `world-run`, so a second harness writing a different name is refused as play too.

## Damage reduces coverage; only records that disagree are contradictions

A real capture arrives damaged in five ways, and each has one correct reading:

- **Killed.** The TSV and the sidecar flush separately, so either may run ahead of the other, the last row may be cut inside its cells and the last occurrence inside its line.
- **Corrupt.** A cell may hold something no reader parses.
- **Respawned.** A new brain restarts comparison, grant and activity identities while attempt identities continue.
- **Old.** An older producer never wrote the evidence.
- **Unopened.** A sidecar may exist and hold no session record.

Every one of those reduces what a check can measure, and none of them is a contradiction. A Definitive finding needs two readable records that disagree. A missing record, an unreadable cell, or a stream with nothing in it is reported where it happens instead: the column audit, the closure check, the occurrence summary's malformed and missing counts, or a named skip.

Two properties follow, and both were violated before the damaged-capture self-test reproduced them:

- **An unreadable identity cell is never compared.** A rule that tests `LongAt(...) != id` counts the null from a corrupt cell as a row naming another attempt, so every identity comparison first requires the cell to parse. Where an exemption rests on cells, as with a strike on the row that closed its attempt, unreadable cells leave the record unjudged rather than unexempted.
- **A sidecar the recorder never opened is not a stream.** Event-based checks skip it by name through `CheckEvents.SidecarUnavailable`. Over an empty stream every presence-based rule finds nothing to contradict and would report a clean run it never measured.

A stream that opened and was later cut still runs, because loss can hide a record but cannot make two recorded ones disagree.

`ADamagedCaptureReducesCoverageAndInventsNoContradiction` damages the consistent identity capture each of these ways and drives it through every check and every reader. The readers are the summary, the occurrence summary, the identity join, the chronicle, the multi-run report and the HTML page. None may throw, none may report Definitive, and each variant must name what it lost.

A false completed transfer became checkable at schema 0.26.0, because collection's conclusion now claims a yield and each pickup names the collection attempt whose drop it was. The claim is read from the cargo's transfer ledger, and that ledger is fed only by the contact pickup that writes those pickups, so the pickups under an attempt of the claimed type must deliver at least the claim. The rule runs one way on purpose: the ledger keeps only the latest transfers and can undercount, so a claim below what arrived is not reported. Mining, chopping and pots still claim nothing — tool effects say `yield=unobserved` and pot completions say contents unobserved — so their completions cannot be held to a yield, and an incidental pickup during other work names no attempt and is counted apart.

## Severity is decided by evidence, not by how bad it feels

Control-grant occurrences join activity, decision and navigation evidence in each default time window. They describe changes of movement ownership and hand permission at AI finalisation. Their identity is independent of the choice identity: recovery and downing can apply fresh controls without evaluating a new ordinary choice. Continuous grant columns retain unchanged ownership between occurrences; neither surface proves later physical movement or a native hand effect.

The event reader consumes the sibling `-events.jsonl` automatically. It validates required schema fields, monotonic sequence numbers and explicit session start/end markers. Missing, malformed or interrupted capture is printed as reduced coverage. Default output groups meaningful events across the entire run; `--timeline` preserves each occurrence beside the TSV's continuous movement chronology. Projectile identity includes its spawn generation, so a reused slot cannot connect one shot to another shot's impact. Terrain contact before any recorded enemy contact is reported as an observed obstruction with launch intent and actual impact coordinates; a piercing projectile hitting terrain after an enemy is not labelled as that failure. The reader does not infer the cause from contact alone. Terrain is locally sampled, and unknown regions or sampling delays remain limits on reconstruction.

The categories are the whole point. A report that says "take a look around tick 3000" hands the reading back to whoever asked for it, so every finding lands in one of three places and the boundary between them is what would settle the question.

| | what it means | example |
|---|---|---|
| **definitive** | wrong by construction: the record contradicts itself, or the behaviour breaks a stated rule, and no situation makes it correct | damage taken in a tick scored as danger zero; a returnable count above the reach count; a body driven at 0.9 px/tick that never moves |
| **potential** | wrong in every situation anyone has thought of, and possibly right in one nobody has; the finding says what would settle it | a stretch under threat with nothing fired; a move that took four times its proven ticks; a row holding the lower-scoring weapon, which `TryFire`'s fallback can produce legitimately |
| **oddity** | a shape in the numbers with no rule behind it — for reading, not for fixing, and where the defects nobody has met yet surface first | one action taking most of the session; the torch out in a fight; the session's damage and cost baselines |

Every check is grown from a defect that actually happened, and none exists for a defect that has not. That is deliberate: a check written against an imagined failure fires on the shape its author imagined rather than on the failure, and the cost is paid in every report afterwards.

## Two properties keep it from lying, and both were bought with a defect

**Columns are addressed by name and never by index.** New facts land in the middle of the header whenever the brain grows one, so an index that was right last week reads the neighbouring column this week and reports a number that is wrong by a factor nobody can guess. The parser strips the byte-order mark the writer's UTF-8 stream puts in front of the first column name, without which `tick` is never found and every check reports itself unmeasurable.

**A check declares the columns it cannot work without, and is skipped loudly when one is absent.** Zero findings and zero coverage look identical in a report, so the coverage block prints before the findings and names the missing column for every skipped check. Running against a session from before a column existed is the normal case, not an error: an eight-column-narrower file from 2026-09-08 runs nine of the fourteen checks and says which five it could not.

The cells are not all plain numbers, and a float parse throws on a third of the file: life is `86/100`, self danger carries a trailing `f` on fire (and, in a capture before schema 0.36.0, an `L` in lava), horizon is the word `inf` with no threat in the world, a control is `desired=1.00,0.00`, and the tiles, velocities and wall normals are `x,y` pairs. `Session.ParseNumber` takes the leading number out of every one of those shapes and the suffix is read from the text where it matters; a cell that survives the stripping and still holds no number is counted, and a column with any such cell is reported, because that is the writer and the reader having quietly disagreed.

## What it found on the session it was written against

Run against `2026-09-09_12-29-48.tsv`, the file whose two defects had already been found by hand over a long afternoon, the first version of this tool raised both unprompted plus one nobody had looked for: 774 ticks of hunting at up to 84 tiles from the player, 8 of 10 hits landing while the danger column read zero, and three stretches totalling nearly seven hundred ticks where the body sat at one pixel while being driven at 0.9 px/tick — the platform fall-through freeze, in the same file, in a stretch nobody had opened. That is the pass line the tool was built against and it is worth restating whenever a check is added: a reader that cannot find the defects already known from the file they are in has no coverage, however many checks it lists.

It also found a defect in the instrument on its first run. The scenario capture's dodge detector compared `tick - lastDodgeTick` against a memory window with `lastDodgeTick` initialised to `long.MinValue`, so the subtraction overflowed a signed long and wrapped to a large negative number that passed the test: every hit in a session where no reflex had ever fired was dumped as a hit through a dodge, and the age printed in the window header was −9,223,372,036,854,773,868 ticks. The fix is in `../../Companion/Brain/Infrastructure/Diagnostics/CaptureMovementScenario.cs` and the tell was visible only because this tool prints the window reasons.

## A hit the world dealt is not a hit the companion failed to see

Fire takes life with nothing alive in the room, and so did lava and water until every liquid became air to the orb on 15 September 2026, so the threat sense is *right* to read zero on those ticks, and counting them as unseen hits would turn every cave session into a page of definitive findings. The damage check excludes them the way `ScenarioCapture` does — the `f` suffix on `self_danger`, and in a capture before schema 0.36.0 the `L` suffix and the `hurting` liquid contact as well, which the capture has no reason to exclude because a dodge cannot cause it. A 0.36.0 capture carries neither, because nothing a liquid does takes the orb's life.

Touching a liquid is not the test on its own, and the reason is the shape of a defect the old rule had already been repaired for: the session of 2026-09-08 held two real hits taken while the walking body was submerged but breathing, so excluding on submersion alone would have suppressed two true findings. The orb's form of that repair is `npc_hit`: a recorded hit event on the same tick means something alive dealt the damage, and that is a true finding wherever the body happened to be floating.

Neither exclusion has fired on a real session, because no playtest has yet taken environmental damage. It was exercised on a probe instead: the same 2026-09-08 file with three of its real hits rewritten to carry the lava suffix, which moved the check from eleven hits to eight and named the three as excluded, while the header's own life-lost measurement stayed at eleven events because that number is what the body lost and not what it failed to see.

## Traps

- **A selected `spot` is a destination tile, while the body is in world pixels.** Progress converts the spot to that tile's own centre on both axes before comparing, because the body is a centre too. The walking body's conversion put the target on the tile's floor, since its position was a pair of feet; leaving that in place makes this reader and the arrival check measure the same distance from points eight pixels apart, and mixing the units at all invents a large distance even when the companion has arrived.

- **A check that throws is caught and reported as a finding against the reader**, never swallowed, because a broken check returning nothing is indistinguishable from a clean run.
- **An identity read through `Column.Number` is not the identity.** The number is a float, which stops representing consecutive integers at 2^24, and engine ticks and comparison ids pass that in a long-running host; identity joins parse the cell text as a long.
- **A test fixture that is consistent cannot prove a fallback path.** The attempt join's row routes and its outcome-interval fallback agree whenever every outcome is present, so a deliberately broken row route passed the whole suite until a fixture dropped outcomes; a join with more than one route needs a fixture where only one route can reach the answer.
- **A reused sidecar path can be served from the reader's cache.** `ReadGodsEyeEvents` keeps the last file read while its path, write time and length are unchanged, so a fixture rewritten in place with an equal-length change can read stale; the fixtures write every variant to a fresh temporary stem.
- **A gap allowance is wrong wherever the break in the run is the event being looked for.** `TheHandsWorkWhileThreatened` looks for ticks with nothing fired, so a tick that fired is the boundary of the stretch and not a flicker to be smoothed over; with an allowance of two, the reload ticks between two shots satisfy the condition and the single firing row between them falls inside the allowance, so a healthy two-minute exchange folds into one enormous "nothing fired" finding whose own tally lists the shots it fired. It was written with an allowance because every other check in the file wants one, and it survived a first run only because that session predates the `fire` column and the `shot` flag was sticky through a reload there — which is the shape of defect a check cannot be tested for on a file older than the column it reads.
- **A sticky column is counted by its changes, never by its rows.** `plan_ms` and `flood_ms` stand until the next search replaces them and overstate any per-tick share taken from them; the phase columns are the per-tick ones. The walker's `edge_*` columns were the worst case of this and are gone, but the rule outlives them: anything retained between events is deduplicated on the field that advances, or one occurrence is reported a thousand times.
- **`route_index` is the segment the body is on and stops at `route_points - 2`, not `route_points - 1`.** It is read for progress — a rising index is a segment consumed — and never compared against the point count to ask whether a route is finished. `route_remaining_px` is the column for that question, and it is what the frozen-body check uses, because a length has no convention to get wrong.
- **`npc_vel` is what the contact allowed, not what the brain asked for.** The motor writes the NPC's velocity from the displacement the circle contact let through, so a body pressed into a wall reads a velocity near zero on exactly the ticks a stall check cares about. `desired_vel` is the steering's request after capping and is the column that says a stalled body was being driven. Reading the first for the second turns the definitive form of the freeze check into its potential form, silently.
- **Time on the floor is not a count of deaths.** 766 rows reading `downed` is one down lasting thirteen seconds, and reading the rows as the count produced "downed 613 times" in a report on 2026-09-09. Downs are counted as transitions into the state.
- **One check saying the same thing five times moves the reading cost rather than removing it**, which is the failure this tool exists to fix — and the first version of the fold moved it instead of removing it, which is the sharper form of the same trap. Repeats used to fold *per check*, printing the worst three and one summary whose detail then enumerated all 872 remaining tick spans over two hundred lines; and the closing line counted raw findings while the header counted folded ones, so the 22 September 2026 capture read `DEFINITIVE ISSUES (8)` and closed on `1089 definitive issue(s)`. `Program.Fold` folds **per class** now — a declared `Finding.Class`, or the title with its digits masked — so 875 occurrences of one contradiction are one line carrying the count, the span and eight named spans, while two findings of one check that differ in a *name* stay two lines. A class under three occurrences is not folded at all, because three paragraphs of real numbers beat one paragraph of a count, and a check with more than six classes folds the tail of them so no check can flood the report. Both printed counts are the printed-line count now, with the occurrence total beside them.

## Where a new check goes

**The coverage block names the columns a check could not read; the behaviour parity table names the questions nobody asked.** Those are two different silences and only the first had a home. `Write/WriteBehaviourParity.cs` prints, above the findings, one row per behaviour the README's Behaviour By Behaviour table specifies: the fixtures that grade it headlessly, what this capture's own checks said about it, and — for each disagreement — the ready-to-paste command that cuts a scenario at the tick it happened. Thirteen of that table's thirty-two behaviours had nothing here reading them on 22 September 2026, and none of the thirteen produced a skip line, because a question nobody wrote is indistinguishable from a question that found nothing.

**A check is a detector, and a detector can only find a failure somebody imagined, so the report opens with something that is not one.** Every class here fires on a threshold a person chose, which means a behaviour nobody thought to threshold produces no finding at all — and zero findings is indistinguishable from zero coverage, which is the failure the coverage block was already built to name for *missing columns* and could not name for missing questions. On 2026-09-09 the walking follower completed 1,227 walks, eight drops, no jumps and no fall-throughs in nine minutes; every number was in columns 85 to 90, nothing asked, the session read clean. So the mod writes a census beside each session counting every category whether or not anything happened in it, and this tool prints it above every finding: `Jump: planned 47, begun 1, completed 0` was a row nobody read past, and whatever the orb's census counts, it is printed on the same terms. A missing census is reported by name rather than passed over, because an absent one and an empty one mean opposite things.

**A detector written from one observed failure inherits that failure's extremity, and the partial case then walks past it.** The check that taught this is gone with the walking body, and the lesson is kept because it applies to every detector that replaces it. `EveryMoveOfferedGetsMade` asked whether a kind of move was ever once completed, built from a session where a kind completed *none* of its attempts — so when the same defect returned on 2026-09-11 as 30 completions out of 276 endings, thirty was not none and the check passed the session in silence while the 89% failure rate reached the owner through play instead. Its repair asked for a completion rate against a floor of a half, and three properties of that repair generalise: the floor was a half rather than a fitted number because the claim was that simple and because every kind in every session sat near one or near zero; an interruption was a third outcome rather than a fault, counted apart, because something else claiming the body says nothing about whether the move can be performed; and the never-once case kept its own wording and its own Definitive grade. When reviewing any detector here, the question to ask is which observed failure it was written from and whether a milder instance of the same thing would clear it.

**Two stalls recorded natively exposed gaps in this tool's scope.** These questions now have checks: `CheckFailedMethods` (via `RepeatedFailedMethodsAreFindings` at Definitive severity) names a method that failed more than once with no credited effect. `CheckTheFight` (via `TheHandsWorkWhileThreatened`) recognizes that a hunt refused as `no-reachable-firing-position` is not the target chooser refusing everything — it is a valid refusal with a recorded reason. EngineReplay's `--evidence-scenes` is the offline instrument that produces reproducible test cases from these stall patterns. A hop take-off drowned under the walking body closes a `mine` attempt Failed with zero effects; such a method failure is now recorded and found. An enemy sealed in rock that hunting correctly refuses is no longer reported as the hands refusing — the check reads the hunt offer's eligibility, not only the `reachable` column, so a refusal with a proven reason stays attributed to the place, not to the companion.

**A journey is a unit no check here could see, and two of them now read it — and since the walker went, they are the only movement-timing checks there are.** Schema 0.31.0's `route-episode` and `stop` occurrences make the whole stretch of wanting one place measurable, which matters because a route's segments can each be flown at pace while the journey costs four times its price: the time goes into the gaps between them and no per-segment check can see a gap. `JourneysTakeTheTimeTheyWereProven` reports, per request kind, what the journeys took against their proven total and against the player's own ticks over the same ground, naming the worst five; `TheBodyStopsOnItsOwnRoute` reports the stops with their rate per minute of travel and their split by the reason the producer attributed at the time. Both skip by name on a capture older than 0.31.0, which is every capture on disk as of 2026-09-13, so the skip path is the only one real data has exercised and the fixtures are what proved the rest.

The player comparison is worth naming separately: it is the only reference this tool holds that the brain did not produce. Every other check compares the brain with itself and can therefore only establish internal consistency, which is the limit the diagnostics folder records against its own instruments. A `-` in that column is trail coverage the capture lacked, never a player who was slower, and the finding says so rather than filling the gap with a ratio.

**Deleting a check is a decision this file records, because the alternative is a name in the coverage block that can never fire.** Four movement checks lost their subject when the walking body was retired, and each read a column or an occurrence field the producer stopped writing: a proven edge's tick count, whether a kind of move was ever completed, the distance between two predicted bodies, and a step the macro proof refused. Left in place, every one of them would have kept reporting a clean run for ever while the report listed it as covered — which is the exact failure the coverage block exists to name for a *missing* column and cannot name for a column that is simply never read. `Checks/CLAUDE.md` carries what each of the four read and why nothing stands in its place.

When adding a check, prefer the form with no threshold in it where one exists, and prefer the form that fails loudly when the producer moves. The deleted `EveryMoveOfferedGetsMade` had the first property — it asked whether a kind of move was ever once completed, which has no number to tune — and not the second, which is why it left silently. The fixtures under `Tests/` are where the second property is bought: `RecorderChronologyContractUsesActualLifeColumn` pins the recorder's body, route and steering lines as literal header substrings and asserts no walking-body column has returned, so a rename fails the self-test instead of quietly making a rule unable to fire.

A file per family of question, a class per check, and the class name is the question: `TheBodyMovesWhenDriven`, `HuntingStaysOnHisScreen`. Add it to the array in `Program.cs`, declare every column it reads in `Needs` (including the ones it only reads for the finding's detail, or an old file crashes it instead of skipping it), implement `ICheckCoverage` when it also needs something `Needs` cannot name — registration-derived columns or the occurrence sibling — and put the threshold in a named constant with the reason it is that number in its own comment. State the threshold inside the finding's text as well, because a finding that cannot be argued with is one that gets believed when it is wrong.
