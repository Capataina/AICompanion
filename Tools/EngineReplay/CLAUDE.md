# EngineReplay — the orb's fixtures, run against the installed game with no window

This console tool loads the installed tModLoader assembly headlessly and drives the real brain, the real senses and the real motor over Terraria's own tiles. It opens no window, runs no enemy AI unless a fixture spawns and ticks it, and loads no save file.

**What it is an oracle for changed with the body.** The walker had two bodies — a real NPC under Terraria's box collision, and a portable prediction under a shape approximation — and the suite's centrepiece was a collision matrix proving the two agreed. The orb has one body: the engine's tile collision is switched off for it and the motor runs the mod's own `CircleContact`, the same contact every headless tool runs, from the same source. So there is no second body to match and that matrix has no subject. `VerifyOrbContact` is the contact's proof now, and it proves the size rule directly rather than by agreement with a routine the body no longer uses. What the native suite adds over `Tools/NavReplay` is that this contact reads *Terraria's own tiles*, through the live tile reader, inside a real `CompanionNPC` the game's own AI entry point ticks.

```
EngineReplay/
├─ CLAUDE.md              this guide: the suite as a whole
├─ EngineReplay.csproj    references the mod under the `live` alias, and compiles part of it twice
├─ Program.cs             the entry point and the flag table
├─ ResetProcessState.cs   the per-process and per-case reset every instrument shares
├─ RunOneRow.cs           one named row inside a case: it runs, files its own sub-row, and never stops the rows after it
├─ AuditEveryCase.cs      the decision and effect audits read after every case: a never-legitimate firing fails it, the rest is a measure
├─ VerifyEveryFixtureIsReachable.cs  the reach check: every fixture entry is called from a default case or exempt by name
├─ EmitTimingMeasures.cs  the one way a fixture files a wall-clock figure: a measure tagged timed and sampled, with the regime it ran under
├─ OpenTheRecorderOnACompanion.cs  the one way a fixture opens a recording, and the row that keeps it the only way
├─ Combat/                the stance, its firing, danger, encounter context and safety as a layer on the job, over four children: Activity, Planning, Simulation and Knowledge
├─ DecisionMaking/        the retained course: objective, projection, binding, consequence pricing
├─ Gathering/             ore work, cooperation beside the player, remaining-work accounting
├─ Assistance/            lighting, collection, company hovering, courtesy, capability, the senses
├─ Lifecycle/             spawn and attachment, downing, stat mirroring, doors, HUD, the card
├─ Movement/              contact, free space, routes, following, recovery, liquids, projectiles, and `VerifyEngineMotion`'s default-case table
```

`DecisionMaking/` is the newest folder and it is the one a stranger will not expect from the flag table, because its files are reached two different ways: five run together under `--retained-course-core`, and `VerifyNativeConsequencePricing`, `VerifyWholeCoursePricing` and `VerifyCourseBindingExecution` are named directly in `VerifyEngineMotion`'s default-case table with no flag of their own.

Each child folder's own `CLAUDE.md` owns its fixtures. This file owns what is true of the suite rather than of any one fixture: how a case is run, what the aliases and the reset guarantee, the traps that bite everywhere, and the translation rules a walker-era fixture has to be read through. `Combat/CLAUDE.md` was left untouched by the body change on purpose and was stale on four fixtures on 15 September 2026. That is settled history now: on 21 September that guide was rewritten with a map over all twelve of its top-level files and four children of its own, and all four of those fixtures are folded into it. What follows is the account of what moved in the body change, kept here because it is the change this file is about, and each of the four is now explained where it lives rather than only here. `VerifyHuntAdmissibility` gained a stand-sweep settling loop, without which its sealed-enemy refusal read `firing-position-undecided` rather than a proven absence. `VerifyCombatPurpose` gained a `gate` diagnostic printing the danger numbers its matched scenes are decided from, the same settling loop inside its pursuit scene, and a pursuit world twice as wide so the far reposition still prices a wait past the arsenal's horizon; its spacing row, which moved last, was then rewritten when combat spacing was deleted, and now asserts that a wounded companion weighs the same small attack as more dangerous without any safety response taking the body. `VerifyCombatActorMatrix`'s blocking pillar went from three tiles to twelve, because three was the walking body's height and an arcing shot goes over it — twelve being bounded above as well as below, since a column tall enough to push the flight around it past the arsenal's horizon prices both blocked arms at zero and makes the row comparing them pass against nothing. Each is explained where it lives, and `Combat/CLAUDE.md` now carries all four.

## The default suite is a table of named cases, because the sum it replaced was an abort

`VerifyEngineMotion.Run` once ended in thirty-eight terms of `failed += Verify*.Run()`. Assertions here throw, so that expression was never a total: the first fixture to fail took every fixture after it with it, and the suite returned one exit code that could not distinguish twenty-two unrun fixtures from twenty-two passing ones.

It is a table now — `DefaultCases()` holds one named case per fixture, each run through `EmitLedgerRows.Case` with its own verdict and unable to reach its neighbours. The emitter's reset runs between them, so a case cannot inherit the world its predecessor left. The summed exit code is unchanged, so the suite means what it meant; what changed is that a red names one case and every other case still says what it found. The table is the count; a number written here would be falsified by the next fixture.

**A fixture reachable only through a flag is a fixture the harness has never asked, and a default case now fails when one exists.** `every fixture entry is reachable from the default suite or exempt by name with its reason` (`VerifyEveryFixtureIsReachable`) walks the compiled assembly: a fixture entry is a static, parameterless, `int`-returning method on a type named `Verify*`, `Measure*` or `Fuzz*`, and it is reached when a `DefaultCases()` body calls it, transitively, as read from the bodies' own IL (`call`, `callvirt`, `newobj`, `ldftn`, `ldvirtftn`, so lambdas and local functions count and an aggregate `Run` reaches every row it calls). An unreached entry must sit in the check's `Exempt` list with the reason it is not a default case, and an exemption naming no entry, or one the suite now reaches, is red too, because a stale exemption is how the next fixture would hide. Its first run on 24 September 2026 found 15 of 188 entries hidden: the gathering half of `--retained-course-opportunities`, eight attack-planning rows and two `G04` rows behind `--attack-planning` and `--retained-course-combat`, the `--dodge-repro` reproduction, and three instruments. Eleven are registered now, and three of them had rotted in exactly the way the old paragraph here predicted — `G02 gathering facts cannot mutate after capture` and `G08 incomplete ore census remains unresolved` built ore sites with no captured tool work, which offers no need by design since 22 September, and `G04 captured combat use binds and validates exactly` wrote a use identity from before the target moved into it. All three were fixture rot rather than brain defects and pass repaired. The three exemptions are `--brain-cost`, `--crowd-cost` and `--section-profile`; `MeasureBrainCost.Execute` is the uncomfortable one, because beside its timings it asserts that recording changes no decision, and nothing else in the default suite does. **The rule does not see** a flag-only fixture that takes arguments or is named outside the three prefixes — `RecordEvidenceScenes.Run(args)` and `RenderNativeInterface.Run(root)` are the two today.

**A case's tags live in `CaseTags` beside the table, keyed on its name**, so the table stays one line per fixture. Two tags decide where verify runs a case: `EmitLedgerRows.TimedTag` sends it to the timed lane, which runs after the parallel shards with nothing else on the machine, and `EmitLedgerRows.PerfTierTag` makes it a perf-tier case, skipped by name unless the perf tier is due or `--perf` is passed. A key that names no case throws on the first lookup, because a renamed case that silently lost its tags would change tier with nobody told. `VerifyEngineMotion.CaseSelection` sends every case to exactly one lane, and a shard files no row for a case it did not take.

The case name is the question the fixture answers, written as a sentence, because it is what the scoreboard prints and what `--case` matches. `AIC_LEDGER_CASE` selects by substring and `AIC_LEDGER_RUN` names the run file; a case not selected writes a skip carrying its reason, never silence.

**An assertion inside a case files its own ledger row, keyed `<outer case> :: <row>`, so the run file carries one verdict per assertion and a red row no longer silences the rows after it.** `RunOneRow.Case` and `RunOneRow.GreenOrRed` file the sub-row through `EmitLedgerRows.SubRow` whenever a case is running, and print exactly what they always printed; `GreenOrRed` is the shape the fixtures with their own GREEN/RED helper hand-rolled, any exception being the row's failure. The outer case still files its own row under its unchanged name, so every baseline survives, sub-rows arrive as `new`, and a failing assertion is two red rows: the sub-row naming it and the outer case counting it. The separator carries no `/` because the store keys a row `instrument/suite/case` and `--rerun-red` splits on the slash; a filter naming a sub-row selects its outer case. `Tools/Ledger/CLAUDE.md` owns the emitter's side.

**The gate prefixes are ledger-visible through the sub-rows.** The plan's acceptance gates are tagged as `G13 …`, `G10 …`, `G08 …` prefixes on inner row names, and until 24 September 2026 no run file carried an inner name, so nothing reading `Tools/Ledger/runs/` could say which gates had rows. It can now grep for `:: G13` in a run file. What still does not work is *selecting* by gate: `--case` matches outer names, so `sh Tools/run-case.sh "G13"` still runs only the two outer cases that carry the prefix themselves (`G13 an encounter suppresses work …`, `G10 no domain recomputes …`). **A row belonging to no gate carries no prefix rather than the nearest one** — the vein rows in `Gathering/VerifyVeinRemainingWork.cs` were first tagged `G08`, which is *repairs across domains* and is not what they assert, and the tag came off rather than being traded for another.

**Inside one fixture the abort is gone from the fixtures converted on 24 September 2026, and still real in the ones listed below.** A converted fixture runs every row through `RunOneRow`, and fails afterwards if any did; its `Run` names each row by its method (`RunOneRow.Case(Action, family)` spells `DisabledDoesNotStartAJob` as "disabled does not start a job"), so the conversion adds no second name to drift. Converted: `VerifyOreWork` (35 rows), `VerifyCompanionActivities` (18), `VerifyObservationLifecycle` (10), `VerifyCombatPurpose` (9), `VerifyWeaponLearning` (8), `VerifyKnockbackAwareness` (7), `VerifyHuntProgress` (7), `VerifyItemWeapon` (6), `VerifyHandedGear`, `VerifySafetyIsALayerOnTheJob`, `VerifyHuntAdmissibility`, `VerifyOfferValidity` (4 each), `VerifyCompanionPreferences` (3) and `VerifyUsefulAssistance` (2). Every GREEN/RED helper whose catch took any exception now goes through `GreenOrRed` as well. **Still aborting on the first throw**, because each is one narrative whose later assertions read the state the earlier ones built and splitting it means restructuring the scene: `VerifyCompanionLifecycle`, `VerifyObservedMotion`, `VerifyIntentRegionHoldsThePlayer`, `VerifyFollowRecoveryAndProtection`, `VerifyGodsEyeEvents`, `VerifyRetainedCourseObservation`, `VerifyThreatAnticipation`, `VerifyPreparedActivities`, `VerifyTheParkIsAboutThePlayer`, `VerifyAttackOutcomes`, `VerifyArcLearning`, `VerifyASealedCompanionDoesNotFlyAway`. Not converted to sub-rows, because their helpers catch only `InvalidOperationException` or print the whole stack and the difference is deliberate: `VerifyCapabilityRevision`, `VerifyCourtesy`, `VerifyCompanyIsTheFallback`, `VerifyAccompanyingThePlayer`, `VerifyResponsiveFollowing`. In those, clearing one red can still reveal the next one behind it, which is progress rather than a regression; say which it is when reporting.

**A converted row now runs after a red row for the first time, so a red can bring company.** A row that passed only because the rows before it left the scene a particular way will fail behind a red neighbour it never used to see. That is the order dependence the abort was hiding, not a new defect, and the per-row restoration (`Each`'s `finally` in `VerifyAssistanceTrips` is the shape) is where it is closed.

**A row that is red on something nobody is about to change used to go last in its fixture, and in an unconverted fixture that position is still a decision rather than an accident.** The three reds the rebuild left were all brain findings, and two of them were standing early enough to blind the rest of their file indefinitely: `VerifyCombatPurpose`'s spacing row (rewritten since, when spacing was deleted) stood second of nine and was hiding the pursuit valuation, both protection rows, the two identity rows, the whole of `VerifyEncounterContext` and the whole of `VerifyCombatActorMatrix`, and `VerifyResponsiveFollowing`'s oscillation row stood fourteenth and was hiding all five intent-region rows. Both are last now, with the reason written at the call site. Moving them cost one run each and was worth far more than that: **two of the seven rows uncovered behind the combat one were themselves walker-era defects** — a pursuit premise that never settled its stand sweep, and a pillar three tiles tall because that was a walking body's height — so the file had been reporting one red while carrying three. Clearing those three then uncovered a door row and a horizon premise behind them, and clearing the order leak between cases uncovered a fixture that had passed for months on another fixture's floor. A red that will clear this afternoon stays where it is; a red waiting on somebody's decision is moved, because the alternative is that the rows behind it are unrun for as long as the decision takes.

## Reading a verdict: four formats, and the exit code is the only reliable one

Fixture families report differently, and a grep tuned to one of them silently undercounts:

```
<case name> failed: <ExceptionType>: <message>    the ledger's Case wrapper — most fixtures
<family>: N case(s) failed                        a fixture that counts its own rows
RED <name> / FAIL <name>                          older rows that print their own verdict
Unhandled exception. System.…                     a standalone flag, where nothing wraps the throw
```

A run once showed sixty-four GREEN lines, zero `^RED` and zero "case(s) failed" and still exited 1. **Do not grep for a verdict prefix: read the log end to end and trust the exit code**, or read the run file, which is the only complete account — the suite files 208 rows as of 21 September 2026 and the printed log is longer than that, so a number written here for its length would be wrong within the week. A fixture family's own verdict prefix is never the suite's signal.

The standalone flags are the fourth row's cause and it is structural rather than a defect: `Program.cs` dispatches most flags straight into the fixture, so an assertion escapes as an unhandled exception, which `../Ledger/ExitWithoutACrashReport.cs` prints with the command line and turns into exit 70. Until 24 September 2026 it aborted with 134 instead, and every abort opened a "dotnet quit unexpectedly" dialog on the owner's screen. The same case inside the default suite is caught by the emitter and reported as one red row. A flag exiting 70 and a default-suite case failing with the same message are one failure seen twice.

**Any timing from this suite is comparable only to another taken the same way, and the largest term is how many cases ran before it.** Measured on 21 September 2026 on `combat is admitted only where it can be executed`, which prints its own per-score cost and is therefore the one row that turns a flake into a number:

```
standalone, no harness at all              2.692 ms per score   ▏█████
whole harness, one case, 141 skipped       2.947 ms             ▏█████▌
whole harness, every case running          6.143 / 6.339 ms     ▏████████████▌
```

The harness itself — the build, the boundary check, the ledger, every instrument — costs about a quarter of a millisecond (`6c14e4c`). Running the other two hundred cases first in the same process costs another three and a quarter, and that is the whole of the difference. The one-case run was taken under the same machine load as the failing ones and landed on the standalone figure, so machine load is removed as the explanation rather than merely narrowed. What is left is accumulated process state — heap and collector pressure — because `ResetProcessState` restores statics and rebuilds the tile map and reclaims no memory; the cheap next step is printing total managed memory and the per-generation collection counts at each case boundary, where a monotone climb names heap pressure without a profiler. `AIC-451` carries it.

**This file used to say the opposite, and the inversion is the finding.** The old paragraph warned that a fixture run alone through its own flag pays JIT compilation for the whole planning path on first use where the same fixture inside the default suite does not — so the suite ought to be the *faster* of the two. It is the slower one by a factor of 2.3, with JIT working against the result rather than for it, which is what says the cause is not cold code. The JIT effect is real and still worth knowing for a *lone* instrument (`--combat-cost`'s C1 row is 39 ms cold and 12 ms after the P-rows have compiled the path, which is why those rows exist); it is simply not the dominant term when two runs of one row disagree.

What binds whoever reads a number or a red here:

- **A cost figure taken in-suite is not comparable to one taken alone**, in either direction, and a row that quotes one without saying which it is has not been measured.
- **No wall-clock figure in this suite is a pass line, and none may become one.** The owner ruled on 24 September 2026 that no fixture goes red because something took too long, because "two milliseconds for a specific playthrough might look a lot different than another playthrough". Every timing goes through `EmitTimingMeasures`, which files it as a ledger measure tagged `timed` and `sampled`, and the scoreboard compares it with its own history rather than with a number written into a fixture. What a threshold used to guard — a cache key that stops holding, a scan gone quadratic, a search that stopped honouring its deadline — is a step of several times against a row's own history, which is the shape the relative comparison catches. `AIC-425`, a crowd-cost row that disagreed threefold with itself on one tree, is what a wall-clock line judged in an undeclared regime produces.
- **A case that files a timing carries `EmitLedgerRows.TimedTag` in `VerifyEngineMotion.CaseTags`**, so the scheduler keeps it off a machine shared with a parallel shard, and a case whose subject is cost and whose runtime is minutes carries `PerfTierTag` as well, so an ordinary verify skips it. The crowd planning row is the one perf-tier case, at 138 s of a 232 s suite at `987319df`. A slow case whose subject is behaviour stays in the ordinary tier however long it runs — the door row at 15.5 s and the seeded contract fuzzer at 11.0 s — because skipping it would skip a behaviour, and the decision-cost row at 8.6 s measures bytes and counts rather than time, so it is not timed at all.
- **A regime is read when a timing is filed, not declared by the case.** `EmitTimingMeasures` stamps `production-allowances` or `unbounded-allowances` from `LimitPlanningWork.Unbounded` as it stands at that moment, because two fixtures switch the clock back on inside a case the harness stamped as lifted. A caller that times a budget of its own, as the crowd row does, names the regime explicitly.
- **A slow machine shows as every row of an instrument moving by one factor, and the ledger can say so without a rerun.** Divide each row's `duration_ms` by the same row's in the last green run: a change in the code moves the rows it touches, while a change in the machine moves every row of the instrument by one factor. On 23 September 2026 the `10c6988a` run's engine-replay rows were 1.00x the `987319df` run's for its first sixteen and a median of 4.76x across the 42 after, a step inside one process, while nav-replay sat at 0.97x. That step turned `combat is admitted only where it can be executed` red at 8.2 ms against the 5 ms bound it carried then, and `987319df` itself measured 8.5–9.1 ms standalone in the same minute, which is the red that prompted the ruling above. What slowed the machine is not named: a Minecraft session was running on both sides of the step, so it is not the discriminator, and `kernel_task` at 13.5% CPU suggests throttling without proving it.
- **The ore-work row is still intermittent, and it is not a timing.** `ore work breaks ore without excavating ordinary terrain` went red on 5 of 12 whole-suite runs on 21 September and passed 3 of 3 alone. It asserts behaviour, so it keeps its verdict, and a lone red on it is more likely the neighbours' accumulated state than the change in front of it; a single green whole-suite run is correspondingly weak evidence that nothing broke.

**The regime is half of "the same way", and it is the half that has actually misled somebody.** `Program.cs` lifts the millisecond allowances for the entire process before any flag dispatches, so a cost instrument that does not put the clock back is timing a brain with no deadline. `--crowd-cost` was read that way for a day: 22 ms mean and 814 ms worst, quoted against a 16.67 ms frame and filed as the brain halving the frame rate whenever a fight starts. Under the production clock the same scene is 4.46 ms mean and 15.23 ms worst, inside the frame on every one of 600 ticks. **An unbounded figure is not a frame cost and must never be compared to a frame budget.** What the lifted figure *is* good for is the gap: on that scene the brain wants roughly six times the mean it is allowed, `decide` sits at its 12 ms allowance on 5% of ticks, and the visible price is behavioural rather than dropped frames — combat holds 593 of 600 ticks unbounded and 406 under the clock, with keep-company taking the difference. So the two regimes answer different questions and the instrument prints both, labelled.

## The `live` alias, and the two copies of every static

`EngineReplay.csproj` references the whole mod under the `live` extern alias **and** compiles a handful of movement sources a second time, by an explicit per-file list, into this project itself.

That means **the movement core's statics exist in two copies**, and a reset or a world assignment naming one of them leaves the other holding the previous case's world. `ResetProcessState` writes both deliberately. Anything a fixture sets on `LimitPlanningWork`, `TerrainChanges`, `MovementQueries.World` or the search's world override has to be the `live::` one if the live brain is what reads it.

Three consequences that cost real time:

- **A new file that one of the listed sources calls must be added to the list too.** The mod's own build compiles everything and passes; this project fails with the new name missing, and every run afterwards silently uses the previous binary.
- **Types in a fixture are `live::`-qualified or they do not resolve.** `MovementQueries`, `CircleContact`, `OrbTerrain` and `PlaceTorches` are the ones that bite, as CS0103.
- **Inside an interpolated string an alias-qualified expression must be parenthesised.** `{live::….Count}` compiles as the value `live` followed by a format specifier and fails with *"'&lt;global namespace&gt;' is a namespace but is used like a variable"* (CS0118); `{(live::….Count)}` is the expression. Hoisting the value into a local above the string is clearer than parenthesising and is what most fixtures now do. Search a file for `{live::` before building rather than finding each hole through its own compile error.

One more C# shape costs a build every time it is written: `FormattableString.Invariant($"…" + $"…")` does not compile, because concatenating two interpolated strings yields a `string`. Write one interpolated string, or build the pieces into locals first.

## No wall-clock allowance decides a verdict in the default suite

`EmitLedgerRows.Case` calls a reset before every case, and each instrument registers its own — the engine tier in `ResetProcessState.cs`. The reset lifts the millisecond allowances, leaving each query's work-count limits as the only bound, and returns the statics a case can reach to what a fresh process holds: the planning allowance, the shared clearance field, the search's world override, the terrain record, the census, the tick's published enemy boxes, the section profiler (its tree, snapshot, recording thread and on/off switch), the player's preferences, the diagnostics switches and every actor slot. **This is the restored-statics list's home** — `Tools/CLAUDE.md` names the shared items and points here rather than keeping its own copy, because a list copied into a second guide goes stale one item at a time. Both copies of every static are written, for the reason above. `Main.GameUpdateCount` is the one reachable static deliberately left alone, and the section below says why.

**The reset now *installs* the allowance rather than only clearing it, and that is the harness's half of a production contract rather than a lenience.** Combat's tactical work and the aimer borrow `LimitPlanningWork.Current`, which throws when nothing is standing; in the game `Brain.Tick` always has one open around every one of those calls, so there is no path to that throw in play. A reset that only ended the previous case's allowance therefore left every fixture entering *below* the tick — driving an activity's own `Prepare` rather than a whole tick — with nothing to borrow, and eleven behaviour rows threw `Decision work must begin before borrowing its budget` the moment combat moved off its private budget. The figure installed is the production constant, which the lift above turns into an infinite deadline for every case that is not about a deadline.

**Any process-wide static the reset does not restore is an order dependence waiting to happen, and the reset is the only correct place to fix one.** The class is what matters rather than the instance: a static a fixture writes and the reset never puts back means the next case reads whatever the previous one left, so its verdict depends on the case table's order and on whether it was run alone. Such a case is red in the suite and green on its own, or worse the reverse, and its message usually cannot say which because it asserts a bare equality with no number in it.

`CompanionPreferences.Current` was the live instance and it stood for weeks (`97a9d6d`). It carries six fields any case can write — both work policies, combat, pot breaking, torch placement and the mining list, the distance mode having gone on 26 September 2026 — and `VerifyOreWork.SetUp` set the mining policy and never the chopping one, so its sealed-tree row read whichever chopping policy the process happened to hold. Alone it found the Opportunistic default and passed; inside the suite it found a Disabled or Mimic policy left by a cooperation row, took an early return above the reach block, and reported that retained work re-searches its reach every scoring tick — false in both directions, because the branch was never reached at all rather than reached too often. The row carries the number now (81 after 20 preparations, a counter that never reset, where anything below 20 would have been a genuine re-search).

**The actor slots were the second instance of the same class, and they leaked by accumulation rather than one at a time.** `FillActorSlots` put an object in every empty NPC and player slot and left an occupied one alone, so a hostile a combat row seeded and never killed stayed active into every later case. No single case reddened anything; the sixteen combat and weapon-knowledge cases that run together left enough hostiles standing that `a whole journey is recorded against its proven ticks` — a companion asked to walk to a distant player — fought instead and recorded no journey at all. Bisected on 22 September 2026 with the ledger's `|` case filter (the row green alone, green after any half of the block, red after the whole block), and closed by `EmptyActorSlots`, which gives every NPC, item and projectile slot a fresh inactive object before each case. The three lanes that met it that day had each fixed it in their own fixtures with a `finally`; that fixes the fixtures somebody remembered, and the reset is where the class is closed.

**The third and fourth instances landed together on 22 September 2026, and between them they name the two shapes this class comes in.** One is a *published fact* — a value one component writes for another to read within a tick, so the last case that ran a tick decides what every later case reads. `MovementQueries.Hazards` is that: `CoordinateBrainTick` fills it with the frozen observation's inflated enemy boxes before it chooses, and a case that drives a search directly never writes it at all, so it inherits the previous tick-running case's hostiles. Combat's `HereAndCompany` generator and the company park both walk toward higher enemy clearance through that list, so `a spread weapon closes at full life and holds range at low life` — green alone — read a wounded shotgun closing to 96 px instead of holding 592 px after one tick of `an opportunity the census admits usable is one the binder can still read`. One tick is enough and it does not accumulate, because the field is overwritten per tick.

The other is a *switch a fixture turns off and hands back off*. `CompanionDiagnosticsConfig.Current` is a registered singleton like the preferences, and `BrainTelemetry.Record` closes the session on the first tick it reads `RecordTelemetry` false. `VerifyCombatPurpose.TheRecordCarriesPursuitAimAndHitApart` registers the instance when none exists, records its own scene, and sets the switch to `false` in its `finally` rather than back to what it found. That is the second carrier of `a whole journey is recorded against its proven ticks`, the row `ff30166` half-fixed: the body travels identically with and without it, 30 of 30 ticks owned by `travel` and the same centre to four decimals, and the difference is 8 recorded rows and 27 occurrences against 732 and 299, with no route episode among them.

Three things that hunt generalise. **Restore to the class defaults, never to the value the fixture wanted** — the `finally` that hands a switch back off is indistinguishable from one that restores it, and only the reset can tell. **An accumulation shape is not always accumulation**: the journey row is green after either of its two depositors alone and red after both, so a bisect that halves the list reports "neither half" and stops, and the minimal reproduction has to be found by triples. *Why* it takes two is open — the obvious reading, that one case registers the singleton the other writes, is not what a print of `ModContent.GetInstance<CompanionDiagnosticsConfig>()` inside the reset showed, and nobody should repeat that print expecting it to settle anything. And **the difference that is easiest to see is usually the decoy**: `Main.GameUpdateCount` is 0 alone and 1,000 after one 500-tick case, it was the only other state difference the instrumented run showed, and restoring it left the spread-weapon pair red byte for byte. It is deliberately still not reset — a case needing consecutive observations sets it itself through `VerifyObservedMotion.SetTick`, and zeroing it would hand every static that stamps a tick a future timestamp on the next case.

Two rules came out of it. **Setting the missing field in the fixture is the wrong repair**: it fixes one reader and leaves every other reader of those seven fields with the same dependence, unannounced. And **the honest restore is a fresh instance rather than a list of assignments here**, because every default lives on the property initialisers, so a list would drift from what the game starts with while looking maintained. What it bought is measurable: ore work now fails at the *same* row alone as it does in the suite, where before those were two different assertions and only one was real.

Two more consequences follow from installing the allowance, and both have already bitten:

- **A fixture that drives a whole `Brain.Tick` must not destroy the ambient allowance on its way out.** The tick opens one itself, so the first version of this install turned the eleven throws into four different ones reading `A nested planner cannot replace the decision budget`. `LimitPlanningWork.Own` is the answer: an owner saves what was standing, installs its own and restores the previous one. In production nothing is standing, so it is the `Begin`/`End` pair it always was.
- **A row that supplies its own allowance is asserting something about that allowance, so it takes over rather than borrows.** `CombatFixture.BeginDecision` borrowed an ambient one when active, which silently discarded the explicit budget its caller passed and made the cut that `a useful combat opener fires while broader search is cut` exists to observe stop happening. A supplied budget now wins; only a row with no budget of its own borrows, which is what still keeps a nested call from minting a second deadline.

A case whose subject *is* a deadline keeps the clock, and there are two ways to say so. A whole case tags itself `EmitLedgerRows.ProductionAllowancesTag`. A single row inside an otherwise lifted case saves the regime, turns the lift off, and restores **what it found** — never a literal, because a literal is the current default written down twice, and the day the real default moves every fixture ordered after that row runs under the stale one. The row's own mode is stamped by the emitter rather than passed by the caller, so a row always records the regime the process was actually in.

The walker's three deadline rows went with its planner and no orb row is about a deadline yet; the mechanism stays because the next one will be. Each of the three had announced itself by going red with its own premise assertion rather than by passing quietly — *"the starved run finished its search in one tick, so it proves nothing about deadlines"* — and an orb deadline row is held to the same bar.

## A fixture opens a recording one way, because thirteen sites assembled it by hand and all thirteen left the audit blind

`OpenTheRecorderOnACompanion` is that one way. Before it, seven files wrote the same three lines — construct a `BrainTelemetry`, hand it a mod through `VerifyObservationLifecycle.Attach`, call `OnWorldLoad` — and **not one of them put the companion's body into `Main.npc`**. `ReadLiveCourseForAudit.Read`, the decision audit's own source, reaches the course through `CompanionNPC.Instance`, which is `Main.ActiveNPCs` scanned for the registered type; `VerifyCompanionLifecycle.Create` builds a body with both halves of the `ModNPC` attachment and no slot, so the scan found nothing and the source returned null on every call.

**Nothing went red, and the shape of the silence is the lesson.** The audit counts every decision at the top of its own method, before the source is consulted, so a session in that state reports *every decision audited and zero observations read* — four of the six decision contracts unable to fire, with every row above them green. Measured on the first run of `DecisionMaking/FuzzTheDecisionContracts.cs`: 1,200 decisions audited, 0 observations read, five contract rows green. The second half was the same failure from the other side: `ReadLiveCourseForAudit.Install` is called in play from `BrainTelemetry.Load`, a `ModSystem` override the loader invokes and no fixture did, so even a body in a slot was not enough. The two halves are indistinguishable from outside and the helper does both.

The surface is four entry points, each named for the situation rather than for the step, and `Attach` is gone rather than kept as a delegation — what it did was the half of opening a recorder that a fixture could get right while still leaving the audit blind:

```
Open(recorder, companion)                 a session that will record decisions: mod, body, source, open
AttachWithoutOpening(recorder, companion) everything but the open, for the one caller that decides
                                          whether to record after it already has a companion
OpenWithNoCompanion(recorder, why)        a session with no brain in it, carrying the reason in a
                                          parameter so choosing it is a written decision
Place(companion) / Clear() / Close()      the body into slot 0 and out again, and the recorder's own close
```

**`Clear` gives the audit's sources back as well as the slot**, saving whatever `AuditDecisionContracts.Source` and the effect contract's `BindingSource` held before `Place` installed the live readers and restoring both — usually null, and restoring null is the point. A fixture that installed the reader and left it standing hands the next case an audit reading through a body that case never placed, which is a pass or a fail decided by run order. It is the same rule as the deadline regime above: save what you found, restore what you found, never a literal. What `Clear` deliberately does **not** restore is the previous occupant of slot 0 — it leaves a blank inactive NPC, because restoring a prior occupant is the per-case reset's job and `ResetProcessState.cs` is not this file's to edit.

The body goes in **slot 0** and that is `CompanionNPC.Find`'s doing rather than tidiness: it returns the *first* active NPC whose type matches, so a body placed above another slot carrying the same type would lose the scan to it. `StageRecordedActors` skips slot 0 by its own guard and every combat scene seeds hostiles well above it.

**`VerifyEveryRecordedFixtureIsVisibleToTheAudit` is what keeps it the only way**, and it is a source pin for the reason this folder already pins two refusal literals: the defect is not that a session fails, it is that a session *succeeds* with four contracts inert, so a runtime guard only ever fires on the fixture that already calls it. The row walks every `.cs` under this project, finds each file constructing the mod's recorder, and requires it to name the helper; `Observation/GodsEyeTestStubs.cs` is excused by name because its `BrainTelemetry` is a test-local stub of its own. Beside it, two behaviour rows drive the guard from the state it refuses — with the slot cleared, `CompanionNPC.Instance` must be null, the installed source must hand back nothing and the guard must throw — and one asserts **identity** rather than non-nullness, because a row happy with "something was found" would pass against a body an earlier case left in a lower slot.

Both halves are proved by mutation. Reverting one fixture to the old three-line shape reddens the pin by name: *1 fixture(s) construct the recorder without opening it through OpenTheRecorderOnACompanion … Observation/VerifyCaptureHonesty.cs*. Making the guard return early reddens its own row: *a fixture about to record with a body the audit cannot read was allowed through*. On a clean tree the row reports **8 files constructing the recorder, 1 excused by name, all the rest through the one seam.**

**Two sites deliberately place no body, and they say why in a parameter.** `VerifyZeroTickLifecycleMetadata` and `VerifyRecordingSwitch` are about the recorder's own file lifecycle with no tick behind them, so there is no decision for the audit to read; the reason is an argument rather than a comment precisely so that a site which quietly wants `Open` cannot read identically from outside.

**A fixture that opens through the seam and never calls `Clear` leaves the live reader and a body in slot 0 for the rest of its case.** The per-case reset ends that at the case boundary, so it cannot cross cases, but inside a case every later scene's companion — built by `Create`, in no slot — is judged by a reader that finds no companion. `VerifyCombatPurpose`'s recorded identity scene did exactly that, and the encounter scenes after it had two pickaxe strikes counted as `effect-without-binding` until its `finally` gained the `Clear`. ## The verdict boundary: a fixture never prints its own PASS or FAIL

`Tools/check-navigation-boundary.sh` refuses any file under `Tools/` outside `Tools/Ledger/` that prints `PASS` or `FAIL`. A fixture that decides its verdict in a print looks in a terminal exactly like one that reported, while the ledger never saw it — so it cannot be compared against a baseline, selected by `--case`, rerun by `--rerun-red`, or noticed when it stops running, and every one of those is a silence that reads as health.

A fixture returns a failure count, throws, or calls `EmitLedgerRows.Detail` for a line a person should see; `Detail` prints exactly what the old line printed **and** folds it into the row. `GREEN`, `MEASURE` and plain descriptive lines are all fine — the refused words are `PASS` and `FAIL` specifically.

**`MEASURE` is the suite's word for a number nobody has declared a pass line for**, and it is used deliberately rather than as a way of retiring an inconvenient assertion. A row printed as `MEASURE` says what the body did and asserts nothing about it; the reason it is not asserted belongs in the file beside it.

## Reading a walker-era fixture: seven translations, and each one has bitten

Most of the reds this suite produced during the body change were one of seven shapes. None of them is a brain defect and all of them look like one.

**The body's point is its centre, and `Bottom` is the centre plus a radius.** A walker's assertions rest on feet standing on a floor; the orb's rest on a centre one radius clear of one. Every production caller of `FindToolAccess.InReach` passes `ctx.Npc.Center`, and the parameter is named `centre`; `FindToolAccess.EyeHeight` is zero, with the comment *"the orb's eye and its tools are its centre, and nothing sits above the body"*. A fixture reading the body point from `Bottom` and feeding it to anything reach-shaped, tile-shaped or distance-shaped is wrong by one row on a resting body — which is exactly where a boundary premise lives. Writes are different and are usually fine: `Npc.Bottom = (x, floorRow * 16)` lands the centre one radius above the floor, which is where a resting orb sits.

**A point at the player's feet floors onto the solid floor row.** A standing player's feet sit exactly on a tile boundary and `MovementQueries.Tile` is a plain `MathF.Floor` with no epsilon, so `Tile(player.Bottom)` is the floor itself — a tile no body occupies, which the flood never reaches and every reachability query answers `Unreachable` for. The cell a body actually rests in beside him is one radius up. This one is nastier than it reads because the failure is silent in three different places: a route priced to such a tile returns null and the caller keeps a fallback, a candidate snapped to such a tile is never priced, and a premise asking about it reports a proven absence from a complete region.

**A wall that stops short of the world margin is not a wall.** A pillar spanning the rows between a floor and a ceiling sealed a corridor for a body that walked along it; a flying body goes over the top. Every sealing wall in an orb fixture runs to row 0, and a scene that does not is usually caught by its own closing guard reporting that every case read reachable.

**Reach cannot gate whether work is offered at all.** A body that can hover beside any free cell reaches almost everything, so a premise of the form "at reach N this is refused" only holds at reach 0, and only for a solid target the body cannot occupy. An air target can never be refused by reach.

**State the orb holds permanently cannot witness anything.** `noGravity` and `noTileCollide` are set once at spawn and never cleared, so an assertion that recovery flight sets them passes before recovery starts. Re-express against the motor's own `RecoveryFlight`.

**A fact one component publishes for another has an order, and a fixture that arranges the fact instead cannot see it.** The motor's `ReadLiquid` runs inside `Commit`, at the end of a tick, and decides the liquid from the circle's own contact — then writes `npc.wet` itself, so a hand-set `wet` is both ignored and overwritten. A brain reading `Motor.LiquidKind` at the top of the next tick is reading where the body was when it was last moved. The same one-tick skew governs the settled-speed reason: the sense decides at rest from the velocity the motor wrote last tick, so a fixture must sample the speed *before* `AI()`, not after `AI()` and `AdvanceNative()`. Both skews agree on every tick the answer is obvious and disagree only at the threshold, so they surface as a handful of ticks in hundreds rather than as a broken row.

**A bounded search needs its own clock driven, and each one keys off something different.** The reach flood advances per *rescore*, so it is grown by resolving the positioner. The firing stand sweep is keyed to `Senses.Tick`, so it is grown by advancing that clock — re-preparing an activity four hundred times without moving it re-reads one cached answer for ever. A premise that wants a proven absence must first establish that the relevant search *settled*; an exhausted bound is deliberately not a negative, and a row that reads `…-undecided` is the production rule working rather than failing.

## Traps

- **A scene must observe the world before it prepares, and prime the reach region.** Lighting and work read senses rather than measuring per candidate, so a fixture that writes a light map and immediately prepares is preparing against whatever the last scene left. Call `Senses.Update`, then resolve the positioner until the region is complete. The reach half fails in the opposite direction from the light half: work refuses an unfinished flood rather than walking at it, so an unprimed region makes every row read "not yet known" and the no-offer half of a pair passes for the wrong reason.
- **A stale region is complete, so priming by "resolve while incomplete" does nothing.** A row that edits terrain or moves a body after setup must throw the region away, not merely drive it.
- **Headless, nothing drives `LightingEngine.ProcessArea`,** so the world's own light is whatever a scene last left in the engine's working map, and the engine's own state stays where the last scene put it. Every presenter therefore leaves the engine between a scan and its blur and makes the draw's own observation (`VerifyUsefulAssistance.TakeTheScan`), and the per-case reset forgets both, so one scene's light cannot be read in the next. That would read as a sense defect and is a fixture leak. The light rows empty both that list and the sense's memory of it when they build a scene.
- **Forcing the light field to resample takes a real value, not `int.MaxValue`.** The gate is `++sinceRefresh < RefreshTicks`, so `int.MaxValue` overflows to `int.MinValue` and the sense returns early — the exact opposite of what the caller asked for, silently.
- **Headless, the game's spawn cap is whatever its initialiser left** (five), because `NPC.SpawnNPC` never runs. Any full-brain scene keeping reachable non-boss hostiles weighing more than five spawn slots in front of the observer will read an inferred encounter and zero every optional activity, with nothing in the scene that looks like an encounter. A scene with that many enemies writes the cap it means, as `VerifyEncounterContext` does, or keeps its reachable weight at five or less.
- **Hostile shots go in `Main.projectile[Main.maxProjectiles - 1]` at your peril.** `Main.ActiveProjectiles` iterates only the first `maxProjectiles` entries and the array's last element is the engine's dummy, so a shot placed there exists, reads active, and is never observed.
- **A recorded row with any hostile in it writes `NPC.TypeName`,** which reads `Lang._npcNameCache` — all null until localisation loads. A fixture that records combat supplies `LocalizedText.Empty` for exactly the null entries and restores them afterwards.
- **Loader templates are registered once per content type.** Registering a fresh template per fixture makes `ContentInstance<T>.Instance` null when more than one exists, so isolated tests pass while the combined process fails. Attach each fresh `ModPlayer` through its inherited `Entity` property and keep the one registration.
- **Native tile placement expects every player slot to contain an object,** inactive slots included; a null slot is a fixture defect before it is evidence about placement.
- **A mutation run against a row that sits late in an abort-on-first-failure list proves nothing about that row.** Hoist the row to the front before planting the defect it is supposed to catch.
- **Any case that drives a whole brain tick can poison a downstream geometry row, and the tell is a row that is red in the suite and green alone.** One brain tick of `an opportunity the census admits usable is one the binder can still read` reddens `a spread weapon closes at full life and holds range at low life` on an otherwise pristine tree — a scene that never touches combat, reaching a combat row through a process static nobody named. That is the class rather than the instance, and the instance has been misattributed twice: a whole-tick case was once filed as leaking a residue on the strength of registering it eighth coinciding with four reds, and the bisect then showed it ran *after* the row it was supposed to have poisoned. So the rule is about position rather than about any one fixture: a whole-tick case is a case that writes every static the brain writes, the per-case reset restores the ones somebody has named, and the difference is silent until a geometry row two folders away disagrees with itself. Reordering a case is a diagnostic here and never a fix; naming the static is, and it belongs to `ResetProcessState.cs`.
