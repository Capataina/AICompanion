# Acceptance covers every responsibility, not only the captured failures

**Prepared 12 September 2026. Status: proposed acceptance cases, not executed tests.** The twenty-seven rows below follow the README's responsibility order. Their identifiers are local references for the research, not new gameplay states. They complement E01–E16 by stating what eventual success and a useful countercase look like in play. All three roadmaps end at this matrix; a path cannot declare completion because mining and hunting alone improved.

The authority for each expectation is the [README's Behaviour By Behaviour table](../../README.md#behaviour-by-behaviour), including the owner's latest clarifications. The [eighteen synthesised requirements](<../Decision Architecture/Behaviour, Opportunities and Comparison Criteria.md#accepted-requirements-and-unresolved-choices-stay-distinct>) group those obligations for architectural comparison. This matrix retains their separate observable responsibilities so that grouping does not erase a difficult case.

## One acceptance case has several independent outcomes

Use a named starting state, player trace, capability profile, supported observation set and capture manifest. Declare which actions are physically possible using an independent native check where available. Preserve cases the actor cannot resolve: refusing every opportunity must not count as perfect safety or accuracy. Record the action actually attempted, its granted controls, resulting native effect and the other useful opportunities declined.

The positive and countercase in each row are a minimum pair, not a sufficient statistical sample. Repeat stochastic encounters at independently varied seeds and held-out geometries; estimate uncertainty over encounters rather than treating thousands of correlated ticks as independent trials. Choose numerical pass lines before evaluating a change, from the behavioural tolerance being tested and the recorded baseline. Where the README specifies responsiveness such as noticing a new opening within a second, preserve that as the product target and report misses explicitly. Do not silently relax it to whatever an implementation achieved.

## Companionship and contextual choice

| Case / responsibility | Positive case and changed circumstance | Evidence needed and failure branch |
|---|---|---|
| A01 — Getting out of the player's way | Approach a narrow passage while the companion occupies the usable space; then aim a placeable block at its position. It should clear the interference in time. Repeat with a non-placeable weapon and with a valuable defensive pose: a harmless glance should not cause skittering or abandonment. | Record actual body/cursor/placement or passage conflict, destination alternatives and the final controls. Missed interference directs work to observation; accurate interference with an inappropriate trade-off directs work to policy. Failed execution of a valid escape belongs to movement. E07/E14/E16. |
| A02 — Boss and event behaviour | Start a boss or supported world event while work is underway. Optional work loses relevance, manoeuvring widens, self-preservation precedes damage, and actionable small threats on the player still receive attention. Repeat with ordinary cave danger, an unfamiliar event and player death. Shared safety must also escape environmental danger with no enemy or ordinary activity; no separate Survival child is required. | Distinguish recognised encounter context from inferred combat pressure and unavailable foreign-event knowledge. Record optional detours, effective damage, useful shots and separation. Recognition failure is an integration gap; correct context with distracting work is a policy failure. Broad mod-event compatibility cannot be inferred from one vanilla boss. E06/E14/E15/E16. |
| A03 — Reading where the player is going | Use the same chamber for sustained fast travel, a brief reversal and repeated local torch placement. The companion should stay with sustained travel without overshooting every small turn; local activity should allow independent nearby help. | Record the player trace, inferred context with confidence, excursion duration and useful work. A correct context ignored by selection differs from a bad intent estimate. Compare both against a distance-only baseline. E14. |
| A05 — Chaining several jobs into one trip | Put a pot, dark corner and ore on a useful journey, then move the pot far aside or introduce urgent danger. Cheap incidental work should fit; the costly detour or obsolete itinerary should be dropped. | Record marginal travel, action cost, output, player delay and the opportunity set. If local re-evaluation succeeds, no planner is required. If a missed enabling dependency causes the failure under identical observations, E13 compares planning. E03/E13/E14. |
| A06 — Knowing what it cannot do | Offer one known impossible target, one unresolved target with a safe intermediate approach and one whose first irreversible step has no return evidence. It should distinguish them. Then open terrain or improve its abilities. | Record forward/return query status, explored scope, stopping cause and safe terminal evidence. False refusal points to coverage; false certainty points to uncertainty handling; persistence after a relevant change points to invalidation. E07/E08/E11/E15. |
| A07 — Committing to a decision | Compare nearly finished work with untouched work, holding future cost and context equal when the player supplied the earlier progress. Add a minor distraction, then a serious threat or vanished target. Continuation should be coherent but cancellable. | Measure productive progress, remaining work, target identity, switch costs and reasons. Fewer switches with less useful work is a failed outcome. An inherited body stall or unrelated shot cannot serve as task progress. E03/E05. |
| A19 — Staying with the player | Traverse parallel paths, a high ledge and a route requiring an initial detour away from the player. Compare equal abilities with a faster player or worse terrain on the companion's side. | Measure sustained separation and time to a useful companion position, alongside the native-feasible alternatives. Pair calm known surroundings, credibly trapped enemies and credible approaching danger on identical geometry; allow wider useful work in the first two without requiring combat to tighten companionship in the third. With no worthwhile work, safe relaxed movement and rest around the player are legitimate. Legitimate physical disadvantage is distinct from a policy that always trails. Separate bad destination from failed traversal. E02/E09/E14. |
| A22 — Recovering when it cannot follow | Put the player in an unreachable region while useful local work remains. The companion should remain useful instead of standing at the nearest wall. Remove local opportunities, then vary player separation enough to exercise ordinary-follow recovery. | Record feasible local work, reason for abandoning it, recovery admission/termination and every position update. No teleport is permitted. A nearby sealed case must not gain distant-follow recovery merely because work would benefit. Local usefulness and timely reunion must both be judged; maximising one alone can violate the other. E05/E08/E14/E15. |

## Combat, physical movement and shared actions

| Case / responsibility | Positive case and changed circumstance | Evidence needed and failure branch |
|---|---|---|
| A04 — Enemy selection | Offer a legal shot at a harmful nearby enemy, a harmless distant enemy and an enemy behind terrain. Change who is threatened and whether a useful reachable firing position exists. | Keep current firing target, pursuit target, candidate coverage and threat estimates separate. A null current shot is not a proof against repositioning. If a useful target never enters the candidates, fix admission before ranking. E06/E07. |
| A08 — Firing position | Begin without a current shot but with a native-valid position, including a narrow ledge and an arcing projectile opportunity. Then move the enemy or close the opening. | Require arrival to enable the intended useful shot under actual target/weapon state. A reached waypoint is insufficient. Candidate omission, stale proof, invalid trajectory and native execution are separate failure branches. E02/E07/E10. |
| A09 — Self-preservation | Compare a breathable pool, a deep pool with finite air, hostile water and a sealed pocket. Vary effective incoming damage and remaining life. The companion should escape where escape is feasible and remove danger where retreat is not. | Record native damage, breath, safe-terminal duration and resource-feasible exits. A collision-free prefix ending underwater is not success. If the only modelled escape exceeds available air, add resource state or reject the route rather than raising a survival weight. E06/E08/E10. |
| A11 — Deciding what counts as a threat | Compare a contained harmless creature, a wall-ignoring hostile and a blocked enemy that can still attack remotely. Repeat with an unfamiliar modded attack whose future is unknown. | Preserve effective-harm evidence and its uncertainty independently from companion attackability. A wall or failed route query cannot erase a possible projectile threat. Trace whether the failure is unsupported observation, forecast error or preference. E06/E15. |
| A12 — Traversing terrain | Execute walks, drops, platform descent and jumps over shaped terrain from varied actual velocities, support and liquid states. Add knockback or a terrain change during the move. | Measure actual entry, predicted terminal, native terminal and stable readiness for the next move. Touching a ledge then sliding off fails the landing objective. Interruptions need identity and cause; they are not automatically physical faults. E09/E10. |
| A13 — Protecting the player | Approach the player with threats whose time-to-harm and effective harm vary while the companion works nearby. A distant weak threat can allow finishing; urgent preventable harm should prompt useful intervention. | Measure time to intervene, attack opportunity, harm prevented and cost to the companion. If the actor cannot intervene, standing nearer is not protection. Good threat estimates with late arrival suggest positioning, computation or control delay; bad estimates require E06. |
| A15 — Dodging and kiting | Compare retreat, jump, platform drop and terrain cover while legal shots remain available. Then remove the escape or consume a needed movement resource. | Measure actual damage and useful firing across the whole manoeuvre, including the landing and next threat. A dodge that avoids the first projectile but creates greater harm fails. Keep coherent tool interruption distinct from independent travel shooting. E05/E06/E10. |
| A18 — Finding a route | Use an away-first C-turn, a route under water, a climb over a ceiling and a known sealed region. Open a new route during search and compare different query budgets. | Record transition coverage, search stop, retained work and time to a usable first control. Missing edges, state aliasing, inadequate work allocation and stale results lead to different branches. A* versus D* is compared on the same adequate graph, with native execution held constant. E08/E09/E12. |
| A21 — Weapon selection | Give the closed kit targets with different range, alignment, damageability and finishing opportunities. Add a new authored weapon profile, then test one-weapon availability. Repeat while travelling, using a pickaxe and holding a torch. | Measure legal useful shots and native effects, not animation count. Confirm current feasibility and candidate denominator. Pick/axe cooldown gaps must not create weapon weaving; held torch can yield. Generic player inventory support is outside the acceptance case. E05/E06/E15. |
| A24 — Movement abilities | Revisit the same ledge, water route and resource-sensitive round trip before and after a capability gain or loss. Include combined jumps/dash and a change during approach. | Route, local controls, tool reach, risk and memory must agree on the actual capabilities and consumed resources. A return dependent on a jump already spent fails even if the outward move succeeds. A capability change invalidates only the dependent evidence, but all such consumers must respond. E10/E11/E15. |
| A25 — Doors | Compare an openable closed door, a door blocked on both sides, a platform permitting one swing direction and a gate. Change the obstruction after a route is found. | Native opening/closing state, approach controls and terrain revision decide success. Refusing an openable door is a false rejection; pushing indefinitely at a blocked one is a false admission. Neither is settled by replacing the global chooser. E07/E09/E15. |

## Work, light, cargo and lifecycle

| Case / responsibility | Positive case and changed circumstance | Evidence needed and failure branch |
|---|---|---|
| A10 — Lighting the area | Put the player in darkness and useful dark passages nearby, including a returnable alcove and a one-way shaft. Then give the player light, exhaust supplied torches or place the candidate inside a protected home. | Measure useful illumination and placement, supplies consumed, player benefit and return evidence. Holding light is separate from placement. If remote darkness was never observed, fix observation rather than score; missing supply or forbidden edit must prevent placement. E07/E14/E15. |
| A14 — Breaking containers | Place a pot on the current journey and another requiring a separate excursion. Repeat during tool use and serious combat. The first may be an incidental hit; a separate collection trip can win when uncertain contents, access, capacity and safe return justify it. A costly trip should lose to better available work. | Record added travel and the hand action causing the native break. A pot label lasting thousands of rows is not useful output. Repair the opportunity's scope or purpose before tuning its continuation. E03/E05/E07. |
| A16 — Opportunistic mining | Use exposed ore, ceiling ore requiring an available jump, an approach at the edge of tool range and forbidden excavation. Join the player's vein, then introduce danger or rapid player departure. | Count native damage/block change, not `mine_status` or swing requests. Require the actual arrived pose to permit work, and the hand claim to remain coherent through strike gaps. Correct choice with zero tool effect directs diagnosis to pose/tool legality. E02/E03/E05/E07. |
| A17 — Reporting what it is doing | Observe approach, active use, reflex interruption, deferred uncertainty, completion and a sealed region with other work still available. | Compare every player-facing statement with the actual controlling activity, granted output and evidence age. A suspended mining activity may be visible as suspended, but cannot be described as currently swinging. Do not announce helplessness while useful alternatives remain. E01/E05/E16. |
| A20 — Looting | Offer cheap ordinary drops, a distant low-value detour, ore in an inescapable pit and a useful pickup after an ability gain. Fill player inventory, then the companion bag. | Record opportunity admission, transfer destinations and quantities, capacity and marginal excursion cost. No duplication or silent loss is permitted. Newly created drops do not impose collection; an unreachable item should become eligible again only when relevant facts change. E03/E07/E14/E15. |
| A23 — Changing the world | Place permitted ore/tree/pot/torch opportunities both inside and outside a home boundary; add a tempting goal requiring ordinary digging, bridging, planting or chest interaction. | Record permission source, proposed edit and actual changed tile/item. Forbidden edits fail absolutely regardless of score or path success. A conservative ambiguous-home refusal remains visible so compatibility is not claimed by silently refusing all work. E07/E15. |
| A26 — Getting up after being downed | Down the companion during work, flight and terrain contact; compare owner-assisted recovery with unattended recovery, and repeat across save/load where supported. | Measure NPC-owned life/downed state, recovery duration, cleared control claims and a safe resumed body. The owner helping should speed recovery without becoming mandatory. Stale tools, entity targets, movement resources or duplicate body owners after revival fail independently of architecture. E05/E15. |
| A27 — Opportunistic chopping | Compare isolated and clustered trees with varied player travel, remaining trunk work and nearby danger. Have the player chop one tree while another is available, then compare shared ore work. | Record tree identity, native hit/completion, coherent axe use and subsequent independent drop valuation. Preference for another tree must not become a blanket exclusion of the player's ore vein. Do not reward elapsed futile effort or force completion when serious danger changes the choice. E03/E05/E07/E14. |

## Each roadmap reaches the same matrix through a different experiment

Path 1 evaluates concrete opportunities and repairs the first broken contract found by these cases. Path 2 must pass the same cases with family/child and phase traces; it additionally fails if group size, enumeration order or double commitment changes an otherwise equivalent choice. Path 3 must pass them with plan preconditions, predicted effects and reconsideration traces; it additionally fails if a gain requires future facts unavailable to the baseline or an irreversible outcome hidden beyond its horizon.

These added tests cannot compensate for a missing responsibility. A plan that chooses elegant detours but cannot respect home protection fails A23. A hierarchy that makes work coherent but delays urgent protection fails A13. A flat chooser that keeps every legal action available but cannot finish useful work fails A07. The matrix evaluates the companion's behaviour first and the proposed machinery only as an explanation or remedy.

Some desired absolutes remain aspirations under finite knowledge: never blocking a future click, responding correctly to every unfamiliar event, or always finding every feasible route. Research must preserve those aspirations while stating exactly what an acceptance set demonstrates. An inability to meet one under declared observation or computation limits triggers a focused product discussion backed by counterexamples; it does not grant permission to weaken the README silently.
