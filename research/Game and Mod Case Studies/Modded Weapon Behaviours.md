# Modded weapon behaviours: the taxonomy an "any handed weapon" companion has to cover

## Verdict

Modded Terraria weapons are varied in the way a large open toolbox is varied, not in the way an unbounded design space is varied: every mechanism this survey found across ten mods and vanilla decomposes into a short, closed list of properties — count-and-pattern of shots, a spawn point, a flight law, a tile response, an enemy response, a hold/charge shape, deployables, and a class resource gate — and every named weapon is a specific composition of two to five of those properties, not a new primitive. Calamity's public source (`CalamityTeam/CalamityModPublic`, read 2026-09-15) alone carries several hundred `ModProjectile` files and not one of them needed a ninth category to describe. What makes the space feel infinite is combination and parameterisation (how many pellets, how much decay per bounce, which curve the homing turn-rate follows), not new kinds of behaviour, and a companion that can represent the taxonomy below compositionally — rather than needing a special case per weapon — is representing the real space. Two things sit outside that closed list and are the genuine hard cases: a projectile's AI reading its owner `Player` object for facts a spawn-time snapshot cannot supply (the cursor, mid-flight; a stealth or charge meter; a resource pool another system drains), which is common enough in modded code that one companion mod (TerraGuardians) built a whole player-identity-swapping layer to cope with it; and a small number of weapons whose behaviour is not fixed per item at all — Metroid Mod's addon-composed beams, Stars Above's aspect-swappable damage types — where the same item ID fires meaningfully different projectiles depending on state the observer cannot see from the shot alone. Everything else is a property to learn and a mechanism to reproduce.

## The property taxonomy

```
Weapon behaviour properties
├─ Launch: count and pattern per use
│  ├─ single                          — most bullets, arrows, thrown items; trivial to learn (one shot per use, fixed origin)
│  ├─ burst / spread                  — Bullet-Filled Shotgun (Calamity): 40 bullets, "extremely large spread"
│  ├─ staggered volley                — Daedalus Stormbow (vanilla): 2–4 arrows per use, cursor-aimed, raining from above
│  ├─ per-frame stream (channel-fired)— Last Prism (vanilla): continuous beams while held, not discrete "uses"
│  └─ random / conditional count      — Daedalus Stormbow: arrow count is itself randomised (1/3 chance) by ammo type
├─ Origin: where the projectile appears
│  ├─ the weapon muzzle / player hand — default for the vast majority (guns, most bows, thrown items)
│  ├─ the sky above the target        — Daedalus Stormbow: arrows spawn overhead and rain toward the cursor
│  ├─ the cursor itself               — several magic "rain"/AoE spells spawn their effect at or near the mouse position rather than the caster
│  ├─ around the target                — Nimbus Rod (vanilla): summons a storm cloud above wherever it lands, which then drops rain projectiles from itself, not from the player
│  └─ around the owner, orbiting      — RealityRuptureLance (Calamity) spawns a rotating dust halo around itself as it travels; whip "tag" auras and Thorium bard orbs orbit the player, not a projectile
├─ Flight law: how it moves after spawning
│  ├─ straight, no gravity            — most bullets, lasers
│  ├─ delayed gravity                 — thrown daggers/axes (AICompanion already learns onset tick + rate); vanilla `ProjAIStyleID.Arrow`
│  ├─ acceleration over time          — SpiritBoomerang-style returning weapons ease outward then reverse; ClubProj (Spirit Mod) has a charge-time-scaled release `Acceleration` field driving the swing
│  ├─ sine/wobble                     — many vanilla "worm"/snake enemy projectiles and several Calamity dust trails use `Math.Sin(time)` offsets purely for visuals, distinct from the collision path
│  ├─ homing (turn-rate steering)     — CondemnationArrowHoming (Calamity): `velocity = (velocity*29 + direction*21) / 30` each tick, a exponential-smoothing turn, not a hard snap; Chlorophyte Bullet (vanilla): homes within 18.75 tiles, "swerves around blocks"; AquashardSplit (Calamity) turns homing on only after `timeLeft < 280`, i.e. after an un-homed travel phase
│  ├─ cursor-steered, continuous       — Last Prism (vanilla): beams sweep toward the live cursor for the whole 3-second channel, with a capped turn rate ("sweeping motion... turn rate is reduced")
│  ├─ cursor-anchored target region (not owner-anchored) — Zenith (vanilla): swords home on enemies within 20 tiles of the *cursor*, "regardless of where the cursor is on the screen" relative to the player
│  ├─ orbiting the owner              — Thorium bard "empowerment" orbs; several Calamity pets circle the player between actions
│  ├─ returning to the owner          — vanilla boomerang `aiStyle=3`, reused directly by SpiritBoomerang (Spirit Mod) with no override; yoyos (held, tethered rather than free-flying)
│  └─ stationary / anchored           — sentries and turrets (see Deployables) do not travel after being placed
├─ Tile response: what happens at a wall
│  ├─ dies on contact                 — default for most projectiles (`tileCollide = true`, no `OnTileCollide` override)
│  ├─ passes through (`tileCollide = false`)  — RealityRuptureLance, RealityRuptureStealth, VividClarityBeam (all Calamity) ignore tiles until a manual re-enable partway through flight
│  ├─ bounces N times                 — Water Bolt (vanilla): up to 5 bounces, and re-accelerates ("moves 6x faster") after each one; Meowmere (vanilla): up to 4 bounces, each one spawning a growing explosion; BouncingShotgunPellet (Calamity): 3 bounces, and the *second-to-last* bounce is redirected at the nearest enemy instead of reflecting normally (see below)
│  ├─ predictive/smart bounce         — BouncingShotgunPellet (Calamity): on its penultimate bounce it searches `Main.ActiveNPCs` for the nearest valid target to the owner's cursor and overwrites its velocity with `CalculatePredictiveAimToTargetMaxUpdates`, i.e. "bounce toward whichever enemy is nearest the reticle" rather than a physical reflection
│  ├─ sticks / embeds                 — many spears and some arrows set `tileCollide=false` after impact and freeze in place (`velocity = 0`) rather than dying, remaining as a hazard or visual
│  └─ rolls along the surface         — the brief's "bouncing piercing ball rolled along the floor" pattern is the flight-law + tile-response combination of a low-restitution bounce with friction against ground normal; no example was pinned to a specific file in this pass (named gap below)
├─ Enemy response: what happens on hit
│  ├─ dies after N hits (`penetrate`) — the ordinary case; Calamity ranges from `penetrate=1` (AquashardSplit) to `penetrate=10` (VividClarityBeam) to `penetrate=-1` (infinite, e.g. PulseTurret's beam)
│  ├─ splits into children on hit or on death — AquashardSplit is itself the child of Aquashard; VividClarityBeam spawns a `VividOrb` from `localAI[1]` on a timer *during* flight, not only on hit, and VividOrb in turn calls `CalamityUtils.MagnetSphereHitscan(...)` which fires further `VividBolt` sub-projectiles at nearby enemies — a three-generation spawn chain from one cast
│  ├─ explodes with an area effect     — Meowmere's bounce-triggered rainbow explosion (3×3 growing to 5×5 tiles); RealityRuptureStealth spawns a `SpearofDestinyStealthExplosion` on hit at half damage
│  ├─ chains to the next enemy         — not directly evidenced in this pass at the source level; Calamity's `DoGLaserWalls`-style multi-target lock-on and several "arc lightning" projectiles in other mods are the closest analogue (named gap below)
│  ├─ applies a debuff or a mark that a later hit exploits — SpiritBoomerang (Spirit Mod) applies `SoulBurn` on `OnHitNPC`; the general Calamity/vanilla pattern is any `OnHitNPC` calling `target.AddBuff(...)`, and "exploits" a prior mark by checking `target.HasBuff<T>()` before applying a bonus-damage or bonus-effect branch elsewhere
│  ├─ pierces a boss's whole segmented body (worms) — not independently source-verified in this pass; documented in vanilla wiki prose for high-`penetrate` weapons against worm-type NPCs, treated here as the ordinary high-`penetrate` case rather than a distinct mechanism (named gap below)
│  └─ knocks back / shoves distinctly per weapon — every projectile carries its own `Projectile.knockBack` float read at spawn from the item; nothing evidenced here varies knockback dynamically per hit beyond simple falloff (whip damage-per-pierce falloff is the closest dynamic case)
├─ Held / channelled attacks
│  ├─ charge-then-release              — Charged Blaster Cannon (vanilla): "multiple firing modes with escalating speed, damage, and method of attack depending on how long the Use/Attack key is held"; ClubProj (Spirit Mod): a `ChargeTime` and `Acceleration` pair set per club subtype, read from the item's own `SetStats` call, driving a charge-then-swing animation state machine (`animTime`, `_angularMomentum`, `released` are all synced fields)
│  ├─ continuous beam                  — Last Prism (vanilla): a 3-second convergence with rising mana cost "12 times per second" at the end; releasing the button ends the beam immediately, mid-convergence
│  ├─ yoyo (tethered, held at a leash range) — Spirit Mod's `Yoyo/` folder (11 items); a yoyo is a returning projectile whose `aiStyle` keeps it near the cursor at a bounded string length while the button is held, rather than either "fire and forget" or "swing once"
│  ├─ flail (swung, released, retrieved on a chain) — Spirit Mod's `Flail/SpikeBall.cs`, `VineChainProj.cs`
│  ├─ drill / continuous contact damage — not independently source-verified this pass (named gap)
│  └─ spear / thrust and retract        — Calamity's rogue "Lance" throwables convert to a stab-and-retract pattern for their non-stealth form in several weapons named on the wiki; not opened at source level this pass (named gap)
├─ Deployables
│  ├─ sentries / turrets                — PulseTurret (Calamity, `DraedonsArsenal`): `Projectile.sentry = true`, `timeLeft = Projectile.SentryLifeTime`, targets via `Projectile.Center.MinionHoming(850f, player, false)` every tick, independent of the owner's aim
│  ├─ mines                             — PrismMine, PulseGrenadeProjectile and similar Calamity items: a slow-drifting or stationary trigger volume that detonates on proximity or timer rather than on direct hit
│  ├─ auras                             — Thorium Healer "Auras": a ring around the owner's cursor that buffs allied *players* standing inside it (explicitly does not affect NPCs, per the wiki — see the class-resource section)
│  └─ minions/pets that themselves fire — MinionAI-driven sub-attacks, e.g. `BasicManabond` (Starlight River): a minion that periodically spends a private "mana" pool siphoned from the owning player to fire its own homing `MagicBolt`, entirely independent of the item that summoned it
└─ Class resources: a gate on when/what the weapon can do, read from player state
   ├─ Calamity Rogue "stealth"          — `RealityRuptureStealth.cs` is a wholly separate `ModProjectile` from the normal `RealityRuptureLance`, fired instead of the normal shot when the class's stealth meter is full; it deals different damage, spawns an extra explosion on hit and screenshakes on impact. The wiki (`calamitymod.wiki.gg/wiki/Rogue_weapons`, read 2026-09-15) confirms the general rule — "rogue weapons are able to consume stealth when used, which adds a new attack" — without documenting the exact accrual formula (named gap)
   ├─ Thorium Bard "empowerment"        — a buff applied to the player (and nearby allies) on weapon use, read by every other symphonic weapon to scale damage/speed/movement; the effect lives on the *player*, not the projectile, so a companion reading only its own handed item would never see it unless it also watched the owner's active buffs
   ├─ Thorium Healer "auras"            — heal/buff zones that explicitly exclude NPCs by design ("only allied players able to be healed as NPCs do not receive the healing effect", per `thoriummod.fandom.com/wiki/Healer`, read 2026-09-15) — the one class-resource case in this survey that is structurally inapplicable to a companion NPC rather than merely hard to observe
   ├─ Metroid Mod "overheat meter"      — a heat gauge that fills on every shot (more on charged shots) and locks the weapon out entirely once full, independent of mana or ammo; `terrariamods.wiki.gg/wiki/Metroid_Mod/Power_Beam`, read 2026-09-15
   └─ Starlight River minion-siphoned mana — `BasicManabond.cs`: the minion itself holds a private mana pool (`mp.mana`) that it drains from the owning player at a fixed rate and spends on its own attacks, so the "resource" belongs to neither the weapon item nor the player's normal mana bar
```

### Per-property: implementation, owner-reads, and what an observer needs

| Property | Typical tModLoader implementation | Reads `Main.player[Projectile.owner]` or cursor? | What an observer must record to learn it |
|---|---|---|---|
| Spread/burst count | Item's `Shoot()` override or `UseItem` calls `Projectile.NewProjectile` N times in a loop with per-shot angle offset, or the weapon spawns one "spawner" projectile that itself spawns N children on its first tick | No — count and spread angle are decided once, at cast time, from the item/player's stats (e.g. attack speed does not change count) | Number of projectiles that appear within one game-tick of the use event, and the angular spread between their initial velocities |
| Sky/cursor/remote origin | `Projectile.NewProjectile` is called with a spawn position offset from `player.Center` (e.g. `player.Center - new Vector2(0, 800)`) or from `Main.MouseWorld` rather than the weapon muzzle | Yes, almost always — the offset is computed from the owner's position or cursor at spawn time only, not read again afterward | The spawn position relative to both the owner's position and the owner's cursor position at the same tick, to distinguish "sky above owner" from "at the cursor" |
| Delayed gravity | A tick counter (`ai[]` slot or a named field) gates `velocity.Y += g` starting at tick K, or gravity strength itself ramps (`g *= 1.02f` per tick) | No | The full position/velocity trace for the projectile's lifetime; AICompanion's existing per-projectile-type fit already covers this case |
| Homing (turn-rate steering) | Every tick: find nearest/closest-to-cursor valid NPC within a fixed radius (`ClosestNPCAt`, `MinionHoming`, or a hand-rolled loop over `Main.ActiveNPCs`), then blend `velocity` toward the direction to that target by a fixed weight (CondemnationArrowHoming's `(v*29 + dir*21)/30` is a literal exponential smoothing constant) | Sometimes — the *search radius origin* is usually the projectile itself, but the *validity filter* (`CanBeChasedBy`) and target-priority tie-breaks can read the owner's cursor (BouncingShotgunPellet explicitly ranks candidate targets by distance to `owner.ClampedMouseWorld()`, not to the projectile) | The blend/turn-rate constant (fit as an exponential decay toward the nearest enemy's position each tick), the activation radius, and whether homing is active from tick 0 or gated behind a delay (AquashardSplit only homes after `timeLeft < 280`) |
| Cursor-steered continuous beam | Every tick while `player.channel` is true, the beam's target angle is recomputed from `Main.MouseWorld`, with the actual heading eased toward it at a capped angular rate (never snapping) | Yes, continuously and directly — this is the clearest example of a projectile that cannot be predicted from its spawn state alone, because its instantaneous heading is a live function of wherever the player's mouse currently is | The full heading-vs-time trace *and* a synchronised recording of the owner's live cursor position, so the observer can fit "heading approaches cursor direction at rate r" rather than mistaking the cursor-chase for free-form homing |
| Bounce (fixed) | `OnTileCollide` overridden; the axis of `oldVelocity` that differs from `Projectile.velocity` after the engine's own tile response tells you which axis flipped, and a bounce counter decrements each hit, killing at zero | No | Velocity immediately before and after each tile contact (to fit the restitution/speed-change ratio, e.g. Water Bolt's 6× speed-up), and the bounce index at which behaviour changes (fixed bounces vs a "final" bounce that re-aims) |
| Predictive/smart bounce | On a specific bounce index, the normal reflection is skipped and `velocity` is overwritten with a lead-shot calculation (`CalculatePredictiveAimToTargetMaxUpdates`) toward the nearest valid enemy to the cursor | Yes — reads the owner's cursor to break ties among valid targets | Same as homing, but keyed specifically to the bounce-index trigger rather than to elapsed time, so the observer must correlate "which bounce" with "did the velocity direction stop obeying reflection law" |
| Piercing / penetrate count | `Projectile.penetrate = N` (or `-1` for infinite); the engine's own hit-cooldown (`usesLocalNPCImmunity` + `localNPCHitCooldown`) prevents multi-hitting the same target every tick when `extraUpdates` is high | No | Count of distinct enemies hit before the projectile despawns, and whether damage decays per hit (whips show a documented multiplicative falloff; most simple piercers do not) |
| Split on hit/timer | `OnHitNPC` or a periodic `localAI` timer inside `AI()` calls `Projectile.NewProjectile` for a child type, optionally consuming a fraction of the parent's own damage | No, typically — damage and count for the split are usually pre-computed from the parent's own stats at spawn or hit time | Whether the split fires on impact, on death, or on an internal timer regardless of impact (VividClarityBeam splits into `VividOrb` on a 49-tick clock during ordinary flight, independent of hitting anything) — this distinction is invisible without watching the whole flight, not just the terminal event |
| Explode with area | On `OnHitNPC`/`OnTileCollide`/`Kill`, iterate `Main.ActiveNPCs` within a radius and apply direct damage, or spawn a short-lived hostile-radius `Projectile` that does the AoE itself | No | The radius and whether it scales with some external counter (Meowmere's explosion literally grows with the bounce index, from 3×3 to 5×5) |
| Debuff/mark that a later hit exploits | `OnHitNPC` calls `target.AddBuff(buffType, duration)`; a *different* weapon or system checks `target.HasBuff<T>()` before branching into bonus damage | No | The buff applied (its ID/duration) and, separately, whether any other observed weapon's damage numbers change specifically against marked targets — this is a two-weapon correlation, not observable from one weapon's shots alone |
| Charge-then-release | The held item tracks its own charge timer client-side (often in the `ModItem`'s `Update`/`UseItem`, or via `player.itemAnimation`), and the eventual projectile is spawned with `ai[]` values or a different `ProjectileType` chosen by the charge tier reached before release | Yes — the charge duration is inherently a function of how long the player held the use button, i.e. `player.itemAnimation`/`player.itemTime`, which a companion has no equivalent of unless it tracks its own "how long have I held this weapon down" state | The relationship between hold duration (as measured by the companion's own trigger-hold, since there is no player input to read) and which discrete projectile/tier resulted — effectively a lookup table the observer must build by holding for different durations and recording the outcome each time |
| Continuous channel/beam | `player.channel = true` on the item; the projectile refreshes its `timeLeft` every tick as long as the use button remains down, checked via `player.channel` or `player.itemAnimation > 0` | Yes, directly — a beam projectile frequently reads `Main.player[Projectile.owner].channel` to decide whether to keep extending itself, so a stand-in owner that never sets `channel` will make the beam die after one tick | Whether the projectile's lifetime is capped by a fixed `timeLeft` or is contingent on an external boolean staying true — distinguished by whether killing/interrupting the owner's "hold" ends the beam early in a real capture |
| Yoyo / flail (tethered) | `aiStyle` (vanilla yoyo/flail styles) keeps the projectile at a bounded distance from the owner, reeling in in `AI()` if `Vector2.Distance(Projectile.Center, owner.Center) > maxRange`, or if `owner.itemAnimation` has ended | Yes, every tick — the leash distance is measured against the live owner position, and retrieval is often triggered by an input state (a fresh click) the companion has to synthesise | The leash radius, the retrieval trigger (timeout vs. re-press vs. distance cap), and the tether's own path back to the owner (arc vs. straight line) |
| Sentry/turret (deployable) | `Projectile.sentry = true`, `timeLeft = Projectile.SentryLifeTime`; targets independently via `MinionHoming` against the same NPC-targetting rules as a minion, entirely decoupled from the owner's own aim after placement | Only to check the owner is still alive/in range for despawn purposes; targeting is otherwise independent | Placement position relative to the owner at the moment of use, and that its target selection afterwards no longer correlates with the owner's own facing or cursor — this is what makes it a sentry rather than an aimed shot |
| Mine (deployable) | Slow-drifting or near-stationary projectile with a proximity check (`Vector2.Distance` to nearest NPC) or a fixed fuse (`timeLeft`) gating detonation | No | Whether detonation correlates with NPC proximity (a trigger volume) or with a fixed elapsed time (a fuse), distinguished by placing the mine with and without a nearby enemy present |
| Minion/pet self-fire | A `ModProjectile` with `Projectile.minion = true` runs its own `AI()` targeting loop and calls `NewProjectile` for its own attacks, holding private state (a mana pool, a cooldown) that is not the handed weapon's own item data | Reads the owner to determine which NPC the owner is targeting/nearby, and in Starlight River's case reads the owner's actual mana pool to drain from it | That the "weapon" being handed is not itself the thing attacking — the minion is a second, longer-lived actor whose behaviour must be learned separately from the summon item's own (usually trivial, one-shot) cast behaviour |
| Class-resource gate (stealth/empowerment/overheat) | A counter lives on the `ModPlayer` (Calamity's `CalamityPlayer.rogueStealth`, Thorium's empowerment timers, Metroid's overheat float), and the weapon's `UseItem`/projectile checks that counter before choosing between two entirely different `ModProjectile` classes for the "same" item | Yes, necessarily — the gate is player state by construction, so a companion without an equivalent counter of its own can never trigger the alternate projectile, and an observer watching only projectile output will see what looks like the same weapon firing two unrelated projectile types with no visible trigger | Whichever companion-side counter stands in for the player resource (its own charge/heat/stealth analogue), and the projectile-type switch point relative to that counter reaching a threshold — without a substitute counter, the two projectile types are simply unpredictable from the item alone |

## Prior art

**TerraGuardians (`nakano15/terraguardians`, GitHub, read 2026-09-15)** is the closest existing analogue to AICompanion's problem: a `Companion` class extends `Player` so that the game's own `Main.player[Projectile.owner]` lookups resolve to a real, if synthetic, player object rather than nothing. Its `ProjMod : GlobalProjectile` (`ProjMod.cs`) intercepts every projectile's `PreAI`/`PostAI`: on `PreAI` it temporarily overwrites `Main.myPlayer` to the companion's own player index (so any vanilla or modded code gated on `Projectile.owner == Main.myPlayer` — a common pattern for client-authoritative effects — executes for the companion instead of silently skipping), sets `projectile.owner` to the companion, and fakes `Main.mouseX`/`Main.mouseY` from the companion's own `GetAimedPosition` before restoring the real mouse position in `PostAI`. This is direct, source-level evidence for this survey's Q3 finding: **owner-player reads, and specifically live cursor reads, are common and load-bearing enough in both vanilla and modded projectile code that a serious "let something other than the local player use arbitrary weapons" mod had to build a general identity-and-input-spoofing layer rather than patch individual weapons.** TerraGuardians still falls back to hand-written `WeaponProfile` subclasses (`Weapon Profiles/CrimsonRodWeapon.cs` is the only one shipped) for items whose generic path misbehaves — evidence that even with the spoofing layer in place, a residue of per-weapon special-casing remains necessary for outliers, which is the same shape of problem AICompanion's four-slot, mechanism-not-item-check design is trying to avoid by never running the item's own use code at all.

No dedicated "projectile trajectory preview/simulator" tool or mod was found for tModLoader. The tModLoader wiki's own documentation (`github.com/tModLoader/tModLoader/wiki/Vanilla-Projectile-AIs`, read 2026-09-15) is only an ID-to-`aiStyle` lookup table with no simulator attached, and general web search returned only unrelated Minecraft "trajectory preview" mods. The closest things to trajectory prediction found anywhere in this survey are *in-game aiming aids built by mod authors for their own NPCs and pets*, not general tools: Calamity's `CalamityUtils.CalculatePredictiveAimToTargetMaxUpdates` (used by `BouncingShotgunPellet` to lead a target after its smart bounce) and `CalamityUtils.MinionHoming`/`Projectile.Center.MinionHoming(...)` (used by `PulseTurret` and Starlight River's minion pattern) are both narrow, single-purpose lead-shot calculators baked into one call site each, not a reusable forward-simulation of an arbitrary projectile's own `AI()` for N ticks. This is a negative but load-bearing finding for Q4: **nothing in the modded ecosystem already runs a copy of a projectile's AI ahead of time to preview its path; every mod that needs "where will this shot end up" computes a closed-form lead estimate for its own known projectile type, rather than executing the target projectile's own code speculatively.** AICompanion's own approach — learn a fitted model per projectile type from real emitted shots — has no existing analogue to borrow from and no counter-evidence that a speculative-execution approach was tried and abandoned; it appears to be uncharted rather than contested ground.

## Gaps and things not verified

- **Chain-lightning-to-next-enemy** and **worm-boss segment-specific piercing** were named in the brief's key questions but not pinned to a specific source file in this pass. High-`penetrate` values against worm-type NPCs (whose body is many adjacent hitboxes) appear to be the ordinary piercing mechanism rather than a distinct code path, but this is an inference from the general `penetrate` mechanic, not a verified read of a worm-specific override — flagged at the "inferred" rung rather than "observed".
- **A rolling, floor-hugging, bouncing piercing ball** (named explicitly in the brief) was not matched to a specific weapon file. Water Bolt's bounce-with-speedup and the low-restitution "rests on the diagonal of a slope" terrain behaviour AICompanion's own `CLAUDE.md` already documents for tile collision are the two closest primitives, but no single weapon combining "rolls," "bounces," and "pierces a group" was opened at source level.
- **Thorium Mod, Fargo's Souls Mod, Mod of Redemption, Secrets of the Shadows, Orchid Mod, Consolaria, Clamity, Everglow** have no public, browsable full source repository found in this pass (Thorium and Fargo's Souls in particular appear to develop privately, per search results, with only wiki documentation public); their entries above are wiki-sourced only and should be treated at the "claimed" rather than "observed" rung. Starlight River (`ProjectStarlight/StarlightRiver`) and Spirit Mod (`GabeHasWon/SpiritMod`) do have full public source and were spot-checked; a deeper pass through either could surface more of the taxonomy's rarer branches (Starlight River in particular is known for biome-specific weapon subclasses beyond the one `Manabonds` example opened here).
- **Calamity's exact rogue-stealth accrual formula** (how fast stealth builds, whether standing still or a stealth potion is required, whether it decays on movement) was not found in the wiki page opened (`Rogue_weapons`) and was not chased into `CalamityPlayer.cs` source, which is out of the sampled file set for this pass.
- **The "learned from observed shots" approach's blind spots**, beyond what the taxonomy already implies: (1) any property gated on a *player resource with no companion equivalent* (Thorium empowerment scaling, a rogue stealth meter, an overheat gauge) cannot be learned from shots alone because the same item produces different projectiles at different — invisible-to-the-observer — resource levels, and the only fix is giving the companion its own analogous counter to condition the observation on; (2) any property that depends on *how long the trigger is held* (all charge weapons) requires the companion to have its own notion of hold duration, since it never calls `UseItem` and so never naturally produces a `player.itemAnimation`-equivalent signal to correlate against the resulting projectile tier; (3) a small number of items (Stars Above's aspected weapons, Metroid's addon-composed beams) do not have one fixed behaviour per item ID at all, so "learn this weapon's behaviour" is only well-posed once the companion also knows which configuration/aspect is currently active — otherwise repeated observations of "the same weapon" are actually observations of several different weapons interleaved, which would corrupt a single fitted model; and (4) whip-style "tag" effects and minion-retargeting side effects are only visible by watching *other* actors' behaviour change after a hit, never by watching the tagging projectile alone, so an observation model scoped to "this weapon's own projectile" will structurally never learn this property no matter how much data it sees.
