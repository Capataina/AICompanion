# Terraria NPC and companion boundaries

**Accessed 2026-09-12.** This report confines itself to public tModLoader source/documentation and accessible companion-mod evidence. It does not re-audit AICompanion’s own NPC, navigation or targeting code.

## Installed tModLoader 1.4.4.9 AI boundary

The installed Steam tModLoader is pinned locally by `tModLoader.deps.json` to `tModLoader/1.4.4.9`, and `Tools/EngineReplay/EngineReplay.csproj` references that Steam installation directly. The Steam app manifest identifies build `25047440`; the matched installed binaries at retrieval had SHA-256 `d530e508b2841e66d880ce279a609624b5ab66ce8093eedfa04f47c3d12d485c` for `tModLoader.dll` and `15f7d045c68cc768a791f056f9179b7e3a03ae1e1deabc96b42cfd39726de7b6` for `tModLoader.xml`. This is local, version-matched API documentation rather than a version-adjacent web branch.

`tModLoader.xml` documents `ModNPC.PreAI` with this order: “`if (PreAI()) { VanillaAI() AI() } PostAI()`” (14 quoted tokens). It says `PreAI` returning false prevents vanilla AI and the `AI` hook; it says `AI` runs only if `PreAI` returned true; and it says `PostAI` runs regardless. The same XML says a modded NPC defaults to `aiStyle = -1` and calls that completely custom AI; it warns that borrowing vanilla `aiStyle` is mainly a prototyping tool because it is difficult to customise. These are API-contract facts for the installed 1.4.4.9 build.

This directly matches the relevant current implementation surface. [`CompanionNPC.cs`](../../Companion/CharacterBody/CompanionNPC.cs) sets `NPC.aiStyle = -1` in `SetDefaults` and owns the `ModNPC.AI` tick. Its `AI` samples the last body result through `Motor.Track`, updates breath/downing, invokes `Brain.Tick`, then processes door/pickup/torch/body/telemetry stages. [`CoordinateBrainTick.cs`](../../Companion/Brain/CoordinateBrainTick.cs) orders senses, reflex/utility selection, position resolution and navigation; it explicitly runs `Engage` after movement/reflex decisions so a weapon can fire while feet are controlled elsewhere. [`ApplyControlsToCompanion.cs`](../../Companion/Brain/Infrastructure/Movement/TerrariaIntegration/ApplyControlsToCompanion.cs) is the live motor: `Apply` records one `ControlSource`, calculates a prediction, writes resolved velocity/direction, and is the body boundary that invokes engine step helpers. The folder contracts independently state that the motor is the only live-NPC movement writer.

The source/API combination supports one precise inference: a single `ModNPC.AI` lifecycle can host independently selected feet and hand outputs only if it retains explicit ordering and one live movement/control owner. That inference is about the existing control boundary, not a recommendation to change it. The sources still do not authorize broad claims about player-item use, temporary local-player spoofing, collision correctness, or multiplayer; those have separate code and test evidence.

## What the local body actually owns

The XML hook contract answers *when* the NPC lifecycle runs. The local source answers the finer question of which component is permitted to turn a decision into world effects. This distinction matters because AICompanion is deliberately an NPC, while some capabilities borrow selected player-shaped helpers.

| Surface | Current source boundary | Evidence and limits |
|---|---|---|
| Live body motion | `CompanionMotor.Apply` sets resolved velocity/direction and applies engine step helpers; `Track` turns the next entry state into an observation/prediction-divergence record. | [`ApplyControlsToCompanion.cs`](../../Companion/Brain/Infrastructure/Movement/TerrariaIntegration/ApplyControlsToCompanion.cs). It does not prove every external Terraria/mod position writer is observed or compatible. |
| Feet decision | `Brain.Tick` can give feet to a reflex, survival escape, navigation or recovery flight, each with a named `ControlSource`. | [`CoordinateBrainTick.cs`](../../Companion/Brain/CoordinateBrainTick.cs). It establishes order in this implementation, not that every requested route can execute. |
| Aim/fire hand | `Engage` occurs after feet selection; `Arsenal` rechecks a present trajectory before spawning a closed-kit projectile. | [`Arsenal.cs`](../../Companion/Weapons/Arsenal.cs). It does not use arbitrary player item behaviours. |
| Work hand | Mining/chopping are tools called by selected work actions; `Engage(action)` honours that retained work hand claim. | [`TileMiner.cs`](../../Companion/Brain/Infrastructure/Interactions/Mining/TileMiner.cs), [`TileChopper.cs`](../../Companion/Brain/Infrastructure/Interactions/Chopping/TileChopper.cs). Reflex/recovery call `Engage(null)` and intentionally bypass this retained work claim, so this is not a universal exclusion across every feet path. It does not generalise to modded `Player.ItemCheck` paths. |
| Door and gate effect | Door handling runs after the motor, so it sees the direction requested this tick; it calls native open/shift helpers and informs terrain-change memory. | [`DoorOpener.cs`](../../Companion/Brain/Infrastructure/Interactions/Doors/DoorOpener.cs). It establishes a bounded route interaction, not general building authority. |
| Light/placement | A held torch is a free, dry-hand presentation/light effect; supplied placement checks policy and Smart Cursor recommendation before native placement, debiting only after observed placement. | [`TorchBearer.cs`](../../Companion/Brain/Infrastructure/Interactions/Torch/TorchBearer.cs), [`PlaceSuppliedTorches.cs`](../../Companion/Brain/Infrastructure/Interactions/Torch/PlaceSuppliedTorches.cs). Reflection-backed Smart Cursor access remains version-sensitive. |

The separation is more specific than a generic FSM-versus-utility debate. A selected movement purpose has no permission to write a pickaxe swing; a tool has no permission to discover its own strategic job; and an aim solution has no permission to claim that the NPC can safely stand at its current or desired tile. This prevents a local algorithm from silently widening its authority because it happens to possess an engine helper.

### Closed-kit weapons: current feasibility is deliberately local

`Arsenal.BestTarget` first forms a bounded candidate list from current threat observations, ordered by urgency then companion distance, and simulates at most four candidates. `ForecastAttack` rejects targets outside a weapon’s declared reach or lacking a solvable/clear trajectory; it then traces potential intersections and only accepts damageable intercepts. A null result therefore means **no useful shot in the examined shortlist from this muzzle, terrain revision and target state**, rather than “no hostile in the world can be attacked.”

`TryFire` makes a second, immediate trajectory check after weapon choice. It preserves a short failed-trace cache only while muzzle, target identity/generation, target pose and terrain revision are unchanged; a movement, changed terrain, despawn/reuse, or target velocity change invalidates the negative result. If the chosen weapon has no current solution it tries the other closed-kit weapon before giving up. After a valid trace it creates the projectile from the NPC’s AI source and records an animation/aim state. This gives the hand channel an explicit present-state admission test, while feet ownership remains elsewhere.

This is useful evidence for the architecture only because the arsenal is closed: its weapon profiles, projectile types, reach, penetration and firing rules are known in source. It must not be promoted into a claim that an arbitrary modded player item can be evaluated, fired or animated safely by the NPC. The work tools make the same distinction. `TileMiner` binds the game’s private pickaxe-damage calculation and invokes a drawing-only player’s `PickTile`; `TileChopper` maintains its own hit-tile state and applies a fixed vanilla-derived axe path. These mechanisms are deliberately explicit abilities, not general delegation to player item use.

### Three local ownership paths, rendered as labelled hypotheticals

*Reflex plus shot.* A projectile/hostile reflex obtains feet first and calls the motor with `combat-reflex`; the coordinator then calls `Engage`. If a work tool has not claimed the arm and the arsenal’s present trace succeeds, a shot is allowed while the body dodges. If no trace exists, no firing claim follows. This is independent output with two admission tests, rather than one action owning the whole NPC.

*Mine plus danger.* A work action chooses an ore tile; only then can `TileMiner.Swing` use its constrained player-shaped mining helper. In the ordinary `Engage(action)` path, the coordinator marks the arsenal `hands-busy`, so a legal combat target does not produce a simultaneous projectile from the same arm. This is not universal: reflex and recovery paths call `Engage(null)` and bypass the retained work claim, which means a source-level review must treat work interruption/release as path-specific. Whether work should be cancelled is a behaviour/commitment question, not a collision-helper question.

*Route door plus torch.* The motor writes this tick’s direction. Door processing afterwards attempts the native door/gate operation in that direction and updates terrain-memory invalidation. If no tool/weapon claims the hand and the NPC is dry, `TorchBearer` may light the held torch; permanent supplied placement remains a separately selected, policy-gated action and only removes inventory after a matching tile actually exists. Thus a route interaction can alter a route fact without becoming a general world-edit scheduler.

These paths are source walkthroughs, not live acceptance evidence. They demonstrate the claim granularity currently available to telemetry: motion source, hand claim, trajectory result, tool outcome and terrain mutation are separate observations. They do not prove the player understands the result or prefers this amount of autonomy.

## TerraGuardians: action override and navigation caveat

The public historical TerraGuardians source ([nakano15/giantsummon, pinned README](https://github.com/nakano15/giantsummon/blob/cf7d9229c1376a525f8cff99d41f70da87013e56/README.md)) separates companions, actions, targeting, compatibility and a `PathFinder`. Its author documentation describes active actions overriding guardian AI until they end, and characterises the custom path finder as an attempt that “doesn’t works correctly.” This is direct author negative evidence: explicit action ownership is legible, whereas a second unproven locomotion implementation is not a precedent for reliable terrain traversal.

The [workshop page](https://steamcommunity.com/workshop/filedetails/?id=2967694381) frames the 1.4 remake as requiring reimplementation and expecting bugs. Thus the public 1.3 source should be treated as historical mechanism evidence, not a current compatibility target.

### Current 1.4.4.9 generation: behaviour components, inventory combat, and recovery fallbacks

The historical repository’s [README pinned at `cf7d9229c1376a525f8cff99d41f70da87013e56` (2024-09-24)](https://github.com/nakano15/giantsummon/blob/cf7d9229c1376a525f8cff99d41f70da87013e56/README.md) links the current 1.4.4.9 codebase. The current public TerraGuardians head retrieved on 2026-09-12 is [`ed1f56bb48e4ccf867ef7732948df5f708526f0d`](https://github.com/nakano15/terraguardians/commit/ed1f56bb48e4ccf867ef7732948df5f708526f0d), authored 2026-09-01. This removes the earlier false implication that only historical companion source was accessible. It does not establish that current code is reliable in live play.

The current architecture is behaviour-component based, with separate [`FollowLeaderBehavior`](https://github.com/nakano15/terraguardians/blob/ed1f56bb48e4ccf867ef7732948df5f708526f0d/Behaviors/FollowLeaderBehavior.cs) and [`CombatBehavior`](https://github.com/nakano15/terraguardians/blob/ed1f56bb48e4ccf867ef7732948df5f708526f0d/Behaviors/CombatBehavior.cs). Follow declines to act when another entity controls the companion, it is mounted, or another behaviour is running. It independently defers to dialogue, active non-`StickClose` combat, active path following, or reviving. These are explicit priority/guard branches, not a utility competition. The project differs at the product boundary as well: it has player orders, controllable companions, mounts, furniture sharing and a full inventory, so its exact policy order is not an AICompanion recommendation.

Follow’s mechanism is nevertheless concrete. It computes horizontal and vertical follow limits from settings; combat increases those limits. At large separation it increments a stuck counter. At 60 stuck increments, it tries `CreatePathingTo(owner, false)` and, if that fails while not in lava and vertically stationary, calls `BePulledByPlayer`; it also clears the revive target and target. The call must be followed into [Companion.cs at the same revision](https://github.com/nakano15/terraguardians/blob/ed1f56bb48e4ccf867ef7732948df5f708526f0d/Companion.cs): the recovery mode moves through collision, can teleport immediately under `TeleportInsteadOfRopePull`, can teleport for large separation or owner knockout, and teleports when the pull completes. Commented teleport calls beside the caller do not establish teleport-free execution. AICompanion's own recovery also moves continuously through terrain, so collision bypass alone is not the difference; its no-teleport contract excludes the conditional and terminal teleports in this fallback. Neither implementation shape establishes reliable ordinary terrain traversal.

Before ordinary horizontal follow, current TerraGuardians checks a large vertical discrepancy and tries pathing; if no path exists and it is grounded above a platform, it requests down/jump controls. It reacts to local dangerous-ahead and hole checks by trying path creation on a 12-tick cooldown, otherwise calling `BePulledByPlayer`; absent those hazards it sets raw left/right movement toward owner position. It separately requests jump for breath/swimming and flight capability conditions. Thus its current follow combines direct control, local obstacle tests, a path attempt, capability gates, and a recovery pull. This is a useful comparison to AICompanion’s explicit movement boundary, but not evidence that one broad `PathFinder` claim applies to all current motion.

Current combat is also a coupled body-and-item policy. It establishes combat memory when a target is near, then refreshes that memory while the target remains within a larger rectangle and `CanHit(target)`; otherwise it decrements memory and clears target at expiry. During engagement, it examines ten inventory slots, rejects unavailable-ammo/mana cases, estimates item damage per second, records strongest candidates by damage class, and selects melee at close range, then magic/ranged/fallback choices. It combines tactic (`CloseRange`, `StickClose`, and others), health danger, hit predicate, attack range, target/owner distance, and vertical melee geometry into left/right/jump/crouch/attack flags. The latest pinned commit specifically adjusted class checks and close-range avoidance, showing this is active current code rather than a frozen historical artefact.

That mechanism differs sharply from AICompanion’s closed-kit trajectory evaluation. TerraGuardians’ inventory scan and item use address a broad player-like loadout; AICompanion explicitly evaluates known weapon profiles and never claims generic player-item use. TerraGuardians also couples combat movement and attack flag production in one behaviour component, whereas AICompanion deliberately lets its coordinator retain a feet decision and decide hands later. Neither design establishes better live companion experience from source alone. The comparison yields a testable boundary: an inventory-generic system pays with broad compatibility/availability predicates and intertwined movement/attack rules; a closed kit pays with narrower ability coverage but allows bounded, inspectable trajectory and hand contracts.

| Current TerraGuardians mechanism | What source establishes | Transfer limit / discriminating question |
|---|---|---|
| Behaviour guards choose follow, combat, path/revive and control exclusions | Explicit branch-based component ownership. | Does a utility selector with separate execution ownership produce fewer unwanted interruptions for this single-companion product? |
| Target-memory window plus `CanHit` | Target retention/release has an explicit temporal and spatial rule. | Should AICompanion retain a combat target over brief threat dips, and do its actual trajectory/urgency facts justify that retention? |
| Path attempt, local hazard checks, then `BePulledByPlayer` | A layered recovery attempt exists, with collision-bypassing movement and conditional/terminal teleports in the called mode. | Teleporting conflicts with AICompanion's contract; continuous recovery through terrain is already permitted. Can ordinary routing and continuous recovery cover separation without importing those teleports? |
| Ten-slot, class-based weapon scan | Broad item-loadout selection is implemented. | Does closed-kit pair evaluation meet desired combat capability without generic item semantics? |

The historical author warning that its old path finder “doesn’t works correctly” remains evidence about that historical component and should not be silently projected onto the current 1.4.4.9 follow component. Conversely, the current source contains no controlled terrain corpus, live success rate, or version-matched user study in this pass, so it cannot establish that the current layered follow or combat policy works reliably. The defensible result is mechanism availability and product/architecture contrast, with live outcome still open.

| Case finding | Supports | Does not support |
|---|---|---|
| Active action overrides default guardian AI | One explicit action/motion owner during a committed action. | A priority/utility formula or safe interruption policy. |
| Separate compatibility surface | Compatibility needs named integration points. | Compatibility with a particular current tML/release ecosystem. |
| Author says pathfinder is unreliable | Movement needs empirical validation. | A diagnosis of why it fails or a replacement navigation design. |

## Transfer question and falsifier

The tentative transfer is not “use action overrides.” It is: give each output surface (feet, hands/tool, aim/fire) a named owner and require a committed action to declare its release/cancellation rule. The countercase is a single all-in-one state machine that proves it can coordinate the same independent outputs with equal traceability and no conflicts. Evidence for either would be live, version-matched traces of ownership, hand state, control writes, cancellations and resulting body motion.
