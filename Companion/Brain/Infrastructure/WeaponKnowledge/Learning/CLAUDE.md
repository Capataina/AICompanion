# Learning — closed traces and closed uses become what a weapon does

```
Learning/
├─ CLAUDE.md
├─ FlightLaw.cs                     the fitted-term vocabulary: gravity, drag, homing, steer-to-aim, return, speed change
├─ FitFlightLaws.cs                 multi-start stagewise fit of those terms from a projectile type's closed traces
├─ LearnWallResponses.cs            what a projectile type does at a wall: dies, passes, reflects, stops
├─ LearnHitResponses.cs             pierce ratio, per-hit damage falloff, area damage, from body hits
├─ LearnChildSpawns.cs              a child type's spawn model: trigger, period, count, offset and velocity in the parent's frame
├─ LearnVolleyShapes.cs             per item, what one press puts into the world: count, and per slot angle, speed, share, origin, delay
├─ LearnWeaponEffectsOnEnemies.cs   push and damage-ratio per weapon item and per enemy type, prior from the decompiled strike arithmetic
└─ LearnAttackOutcomes.cs           the outcome-ratio correction per weapon item, Bayesian linear regression with Thompson sampling
```

Every file here answers one question — what does this projectile type, this weapon, this enemy actually do — from evidence `../Recording/` has already gathered, and every answer is read by `../Simulation/` to price a hypothetical shot before it is fired. Nothing in this folder decides what to fire; `../../Activities/Combat/Planning/` does that, using these tables as the corrected reality the search prices against.

## The shared shape: a prior from the decompiled game, a correction from what was watched

Three of the eight files — `FitFlightLaws`, `LearnWeaponEffectsOnEnemies` and `LearnAttackOutcomes` — share one stance stated explicitly in each of their docstrings: start from what the decompiled game's own arithmetic says should happen, and learn a correction from what the companion's own shots actually did, rather than either trusting the game's numbers blindly or throwing them away and learning from nothing. `LearnWeaponEffectsOnEnemies` calls this out by name as "the same stance as the law fitter." The practical consequence is the same in all three: with zero evidence, every one of these tables returns exactly the prior (a correction factor of one, or the four-number arc law the game would produce), so a fresh save file or a never-fired weapon behaves identically to hard-coded arithmetic, and behaviour only starts to diverge from the prior once the companion has actually fired the weapon in question. This is why none of the tables need a bootstrap phase or a "cold start" special case — the cold-start answer is the prior, by construction, not a branch.

The other structural constant repeated across the folder is **medians over a small, bounded ring, never a running mean over all history.** `LearnWeaponEffectsOnEnemies.SamplesKept` (8) and `LearnVolleyShapes`'s `Distribution.MaxSamples` (16) are both explicit about why: an odd sample — a crit the prior does not model, one strange volley — cannot drag the whole answer, and an enemy or a weapon that has genuinely changed (a mastery grant, a mod that alters a hit) is re-learned from what it does *now* rather than being permanently diluted by what it used to do. `FitFlightLaws` states the same preference for medians over least-squares explicitly, for the same reason.

All of it is **live in memory and all of it is saved with the character.** Every table here is cleared by a process restart and by the engine replay's per-case reset — which is what keeps one fixture's planted evidence from leaking into the next — and every one of them is also exported to the player's save tag and read back on load: `../PersistWeaponKnowledge.ExportAll` bundles volley shapes, flight laws, wall responses, hit responses, child spawns, weapon effects, attack-outcome regressions and debuff counts, and `../../../PlayerIntegration/PersistCompanionState.cs` writes it to `tag["weaponKnowledge"]` and imports it back (verified 22 September 2026). The two facts do not conflict and the distinction matters when reading a fixture: a headless case starts from the prior because nothing loaded a tag, while a played character starts from what it learned last session. Default laws and empty tables export nothing, because a load rebuilds those identically from content.

## Fitting a flight: `FlightLaw.cs` and `FitFlightLaws.cs`

`FlightLaw.cs` is pure vocabulary — six term shapes (`GravityTerm`, `DragTerm`, `SpeedChangeTerm`, `HomingTerm`, `SteerToAimTerm`, `ReturnToOwnerTerm`) that between them describe every projectile flight pattern this game has, each carrying an *onset update* because a term rarely applies from tick zero (a thrown knife flies clean for nineteen updates before its drag begins). A `FlightLaw` composes zero or more of these in one fixed order — speed change, drag, gravity, homing, steer-to-aim, return — so that fitting and flying always agree on which term acts first.

`FitFlightLaws` fits that law from a projectile type's closed traces (`../Recording/RecordProjectileFlights.ClosedFor`) by **multi-start forward stagewise selection with a BIC penalty**: several starts each fit one term first, then greedily add whichever unused term improves the penalised score most, until nothing does, and the best-scoring start across all of them wins. The multi-start is called out as load-bearing rather than a hedge: fitting drag first on a turning flight will absorb the turn into per-axis drag ratios that nothing later can undo, so a homing projectile genuinely needs a start that fits homing first, the same way a falling one needs a start that fits gravity first. Below `MinDiffsToFit` (6) velocity diffs the default law stands untouched rather than fitting noise.

Only *unmodified, use-sample* diffs teach a law. A trace descended from a child spawn never teaches (a retargeting child would bend its parent type's gravity into something that describes the retarget rather than the flight), a trace recorded under a companion modifier (extra pierce, extra projectiles) is excluded whole, because a value that has absorbed a modifier is wrong the instant the modifier changes, and a diff spanning a wall contact is excluded because it holds the reflection rather than the flight — which is precisely the settled-versus-post-AI distinction `../Recording/CLAUDE.md` documents from the other side.

## Reactions to contact: `LearnWallResponses.cs` and `LearnHitResponses.cs`

`LearnWallResponses` classifies a projectile type's behaviour at a tile into one of `WallKind`'s four values — dies, passes through, reflects, or stops dead — from the trace's own `WallContact` records, and for a reflecting type learns per-axis restitution, the speed kept through the bounce, how many contacts precede a wall death, and — the one non-obvious case — whether the *last* bounce departs from simple reflection into a new heading, in which case it records a `HomingTerm` describing the flight from that bounce onward rather than trying to force a reflection law to explain a retarget.

`LearnHitResponses` answers what happens when a projectile's declared pierce meets real bodies: `BodiesPerPenetrate` is a **ratio**, not a fixed count, deliberately, so that a companion-modified pierce (extra pierce from mastery, once that exists) is predicted correctly just by reading the modified instance's declared penetrate times this learned ratio — nothing needs relearning when the modifier changes, because the ratio describes how the *type* converts declared pierce into bodies hit, independent of how much pierce any one instance was given. `KthHitRatio` learns the damage falloff on the second, third, ... contact of one pierce sequence relative to the first. `AreaResponse` is learned rather than declared: a hit whose NPC box never overlapped the projectile's own box (a fact `../Recording/RecordProjectileFlights.BodyHit.BoxOverlapsProjectile` carries) is area damage rather than a contact hit, and its radius and trigger (on death, or on wall contact) are inferred from the pattern of such hits.

## Reproducing a volley and a child spawn: `LearnVolleyShapes.cs` and `LearnChildSpawns.cs`

`LearnVolleyShapes` is the only file in this folder learning from the **player's** uses alone (`../Recording/GroupSpawnsIntoUses.ClosedUses`), for the reason `../Recording/CLAUDE.md` states from the recording side: feeding the companion's own reproductions back in would narrow every slot toward what the companion already fires. Per item it keeps the count distribution and, per slot ordered by delay then angle, the angle, speed ratio, damage share, origin and delay — and it picks the origin kind (`Shooter`, `AtAim`, `AboveAim`, `AroundShooter`) that minimises offset variance across observed uses, which is how a sky-rain weapon's true anchor (a fixed height above the aim point) is discovered without the code ever naming "sky rain" as a case. A use fired under a count-changing buff the companion cannot itself apply is set aside and taught nothing, though the docstring notes no vanilla buff is currently verified to change a count, so this set is empty in practice and the mechanism exists ahead of a case that would need it.

`LearnChildSpawns` groups a parent's recorded `ChildSpawn`s by child type and learns what triggers each (a body hit, a wall contact, the parent's death, or a timer — with the timer's period taken as the median gap between spawns) plus its count, its offset and its velocity, all expressed in the parent's own velocity frame so a rotated shot's children rotate with it rather than needing separate learning per launch angle. Each child type then flies its own separately-learned `FlightLaw`, recursively, to whatever depth of chaining the traces actually show.

## Correcting the arithmetic: `LearnWeaponEffectsOnEnemies.cs` and `LearnAttackOutcomes.cs`

`LearnWeaponEffectsOnEnemies` learns, per weapon item **and** per enemy type, a signed push factor on the decompiled `NPC.StrikeNPC`/`GetIncomingStrikeModifiers` prior and a damage ratio on the arsenal's own damage prediction. The key is the *item* rather than the *projectile*, because a push is the item's own knockback plus its ammo's — the same wooden arrow pushes differently fired from two different bows — and a swing has no projectile identity to key on at all. Only the horizontal component is learned, because only the horizontal side of a push decides whether a struck enemy is carried toward the player or the orb; the vertical pop is left to the game. `../CLAUDE.md`'s own "A hit pushes" section is this file's user-facing story — read it there for why the push was worth learning at all (the owner's 15 September playtest of the companion knocking enemies back into the player) and for the arithmetic `../Interactions/Firing/`'s arsenal charges against a candidate stand using this table.

`LearnAttackOutcomes` is the newest and largest file in the folder and the one with the most machinery: it learns, per weapon item, a **Bayesian linear regression over a seven-number context** (a bias term, distance as a share of reach, aim offset as a share of the widest candidate, target speed relative to the orb, other hostiles along the lane, the orb's own speed, and whether the target is already debuffed by the other weapon), regressing `outcome ratio − 1` — realised yield over forecast yield, clamped, with one minus subtracted so "the forecast was exactly right" sits at the prior mean of zero. It samples via **Thompson sampling**: one coefficient draw per weapon per tick, shared by every stand, target and aim candidate that tick considers, which is what makes the candidates comparable against consistent noise rather than each drawing its own. The intercept is learned **per enemy type** while the context coefficients are shared across types but fit only from within-type variation — a deliberate fixed-effects structure chosen after two simpler shapes were tried and rejected on measured evidence (a shared intercept let three missed shots against one enemy type poison an unrelated, never-shot type; letting each type carry its own residual against a raw-context-fit coefficient carried the same contamination through the coefficient instead). Exploration is suppressed — every forecast reads the posterior mean rather than a fresh draw — whenever a threat's urgency to either the player or the companion crosses a declared ceiling, so the companion does not experiment with a worse attack while someone is about to be hurt.

## Traps

**A term that would explain a flight and a term that actually generated it can look identical on too little data, and `MinDiffsToFit` is the whole defence.** Below six diffs the fitter does not try; above it, the multi-start protocol exists because a single greedy fit can lock in an explanation (drag absorbing a turn) that later terms can never undo.

**`LearnAttackOutcomes`'s shared-context, per-type-intercept split is not an arbitrary modelling choice — it was chosen after two other shapes measurably contaminated one enemy type's estimate with another's.** Reverting to a simpler shared-intercept form reintroduces the exact contamination the current form exists to prevent; this is recorded in `../CLAUDE.md`'s own combat-knowledge section with the measured counts (three demon-eye misses driving a never-shot zombie to a 0.36 mean factor).

**Every table here forgets on process restart and on the engine replay's per-case reset, and none of it is a bug to fix — but it does not forget across a character save.** A fixture that plants evidence in one case and expects it gone in the next relies on the reset; a fixture that expects evidence to persist across cases is testing a guarantee this folder does not offer. In the game the opposite trap applies: a behaviour that looks like a fresh-prior behaviour in a fixture may be running on a table loaded off the character tag, so a play report about what the companion "always" does is a report about that character's learned state.

**`ApplyCompanionModifiers.Current()` (in `../Simulation/`) is what a modified trace is excluded on, not a per-file flag re-derived independently in each learner.** A learner checking modifier state some other way risks disagreeing with `FitFlightLaws`'s own exclusion test.

## Relations

`../Recording/` is this folder's only source of evidence — `RecordProjectileFlights.ClosedFor` and `GroupSpawnsIntoUses.ClosedUses`. `../Simulation/SimulateUse.cs` and `SolveAims.cs` are this folder's only production readers, pricing a hypothetical shot by composing these tables with the decompiled arithmetic. `../../Interactions/Firing/`'s arsenal reads `LearnWeaponEffectsOnEnemies` directly for the push charge described in `../CLAUDE.md`. `../../Activities/Combat/Planning/`'s search prices its candidates through the simulator, never through these tables directly. `../PersistWeaponKnowledge.cs` is the only file in `../` that saves any of this across a character save, and it saves all of it: volleys, laws, walls, hits, children, effects, outcomes and debuffs.
